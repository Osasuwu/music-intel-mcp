## Multi-user pilot — centralized processing node (grill 2026-09-05/06, AC locked)

**Why this section exists.** Phone-only listeners cannot capture or process audio (#118), so a single-machine, all-local design excludes most of the target audience. The pilot introduces a **processing node** (the owner's PC) that runs the same engine for people who have no PC. Terms below are pilot-scoped; `INVARIANTS.md` was amended in the same grill (decision `d0979cce`: locality invariants replaced by purpose limitation).

- **User type A (has a PC)** — runs the full local system; sub-split by where they listen: PC-only (capture + history complete) vs PC+phone (phone listening time yields zero audio, history still arrives via ESH). Background playback on the PC is a must-have for type A to recover the phone-time gap.
- **User type B (phone-only)** — sends a one-shot Extended Streaming History to the processing node and receives their **RootProfile file** back (roots + inclinations, JSON plus a phone-readable rendering). Audio for their tracks is obtained by replay on the node. Continuous history via the recently-played API is deferred until after the pilot (decision `f53ca427`).
- **Processing node** — a machine the participant explicitly chose to process their data (pilot: the owner's PC). Runs the same engine as type A; nothing else about the engine differs.
- **Replay** (decision `81859701`, refining `12681cbc`) — automated playback of not-yet-analyzed tracks on the node to obtain audio for capture. Capture is device-side and service-agnostic; only the playback **driver** is per service, injected through the existing `play_track` callable of `run_automated_playback` (`automated_playback.py`): the Spotify Web API driver (exists) plus one **browser-URL driver** for YouTube Music (video id from Takeout → `youtube.com/watch?v=`) — **deferred post-pilot** (decision `d6c9ffe0`); the pilot ships only the Takeout importer and a `youtube_id` identity field. Runs on a **dedicated account per service** (Spotify Premium, YouTube Premium so ads never reach the capture, SoundCloud Go+ where needed) in a dedicated browser profile with autoplay allowed, never on a friend's token or the owner's personal account. In replay mode **identity is known a priori from the queue** — fingerprinting is skipped, so SoundCloud's missing AcoustID coverage does not affect replay (it still affects organic SoundCloud capture). Replay advances after the ~120 s capture window rather than waiting for the track to end (~30 tracks/h instead of ~17). Cross-service resolution to a Spotify ID is a fallback only when no native driver exists; no cross-client routing (e.g. YouTube as a universal backend) in the pilot. Replay fills idle time only: whenever organic music is playing on the node, capture follows it and replay stays paused. **Slice 1 shipped** (#159): `SpotifyPlaybackClient.resolve_device_id`/`play` now require a resolved `device_id` (`DeviceNotResolvedError`/`DeviceNotFoundError` on miss), `account_is_busy` gates against `GET /me/player`, and `attempt_play` bounds 404/403 retry with a journaled reason, requeueing via `TrackSkipped` back into `run_automated_playback`'s live queue; the CLI's `automated-playback` subcommand takes a required `--device-name`. **Capture contract shipped** (#166): `replay_capture.py`'s `run_replay_capture`/`process_replay_queue` — a dedicated entry point, not a `run_live_capture_spike` code path — take identity straight from the queue's `TrackRef` via `canonical_track_id`. Still open: the organic-yield check.
- **Pilot success criterion** (decision `30b40b80`) — proves the collection pipeline, not recommendation quality: per participant, a RootProfile with timbre clusters over ≥X% of their tracks with ≥3 plays, recognized by them in a blind description; plus the real cross-user overlap coefficient measured from ESH before any audio work. **X = 80** (refined 2026-09-05): the remaining ~20% is what does not resolve to a playable URL, was removed from the service, or is region-locked; below 80 means the service path leaks, which is exactly the conclusion the pilot must be able to give.
- **Node retention** (decision `92241497`) — a participant's personal data (history, replay queue, profile) exists on the node only for the duration of their run and is deleted once the RootProfile file is delivered; only the anonymous track-level analysis pool persists. Trust boundary in the pilot is the node owner, stated openly to participants; at-rest encryption on the owner's own machine is hygiene, not a guarantee against the owner. Direct-to-program ingestion via an API is deferred past the pilot.
- **Dedicated replay client runs the Spotify web player in a browser tab** (refining, under decision `12681cbc`) — the desktop client allows one instance per Windows user, and the browser path also exercises the unverified browser-capture route.
- **MTG outputs are pooled in the closed pilot** (licence footing **confirmed by MTG 2026-09-15**, decision `ad39cbcd-035c-487d-94eb-04c6f3ea081e`: model outputs are outside CC BY-NC-ND's no-derivatives scope; decision `6c1e2ebc`, dual-embedding part **superseded** by `45fe71d6`, itself **resolved** by `24458ec3-eb48-4714-bae3-23f387517f16` per #118) — treated as non-commercial research use; CC BY-NC-ND reading reconfirmed by `35bc7c5b-bade-44a0-86a7-479967c89e7a` (#118). The pilot embeds with MTG only: no PANNs code, weights, or dependency exist and `AudioAnalysisRecord` holds exactly one embedding. #118's research resolved the dual-embedding question: keep MTG primary/unchanged, add PANNs as an additive optional `embedding_panns` field scoped to the pooled/shared-tier record only (PANNs code is MIT, pretrained weights are CC BY 4.0). MTG's 2026-09-15 reply removes the licence motive for that field; it stays unbuilt and returns only if an evaluation reason turns up (decision `ad39cbcd-035c-487d-94eb-04c6f3ea081e`). What stays: a runtime RSS guard (psutil) and a loud failure when model files are missing (today `inference.py` falls back silently).
- **Type B deliverable is the RootProfile file** (decision `2a945d43`) — the roots/inclinations file is the project's primary goal; playlist push / recommendations are secondary and must be designed for, not shipped, in the pilot.
- **Three single-person service paths** (decision `871ef598`) — participants are three friends, one per service (Spotify, YouTube Music, SoundCloud), so the service axis coincides with the person axis and cannot be separated at n=3. Slice order: Spotify (owner + participant, code exists today) → YouTube Music (Google Takeout `watch-history.json` importer; entries carry `header: "YouTube Music"`, title, video id, channel, time, no `ms_played`, and Google's default 36-month auto-delete makes it lossy) → ~~SoundCloud~~ (dropped, decision `ba589810`: no history export). **Stated limit of the pilot's conclusions:** it licenses "each service path works end-to-end on one person"; overlap savings and recognition rate at n=3 are anecdotes, not measurements. Overlap is measurable only owner vs the Spotify participant. Apple Music export exists (privacy.apple.com, `Apple Music Play Activity.csv`) but no participant uses it.
- **Node store layout** (decision `1fe8e95f`) — one transient per-participant data root (`data/participants/<id>/`, the existing `UserStore(root=...)`) plus a node-level anonymous pool `data/pool/audio_analysis/`; `has_audio_analysis` consults the pool first and every new analysis is written to the pool, never to the participant root. Participant roots are deleted after delivery, the pool persists (per `92241497`). **CLI surface shipped for #165 (`9fbaac14`)**: `--data-dir` on `music-intel-desktop` and every CLI subcommand that opens a `UserStore` selects the per-participant root (Spotify token and consent file live inside it, so they're per-root too); `music-intel purge --data-dir <root> [--force]` deletes that root with `shutil.rmtree` and never touches the pool or a `SharedStore` (sibling paths by construction, no nesting) — it refuses (exit 2) when `UserStore.latest_profile()` is `None` (no `RootProfile` delivered yet), `--force` bypasses the refusal; the consent file (`automated_playback_consent.json`) now stores `{"grantor", "timestamp", "scope"}`, and `has_automated_playback_consent()` raises `ConsentFormatError` on an old file missing `grantor`/`scope` rather than silently treating it as ungranted.
- **Type A replay on a dedicated per-participant account on the participant's own PC** (decision `909d28fe`, partially reversing `8457e9b2`) — replay on the participant's own account cannot be kept out of their later ESH export: local replay events are stamped at play start, export rows at stream end, dedup keys on exact `played_at`, so a re-import returns every replay as organic `spotify_extended` signal, and the replays also train Spotify's recommender on the friend's account. Each participant therefore gets an account on the owner's family plan, used only for replay, in a **browser different from their daily one** (a separate exe stem is a separate process tree for loopback). A **replay-window ledger** (start/end per participant) is the second defence: the importer tags export rows inside a window as agent-originated. Kept from `8457e9b2`: the account-state gate (`GET /me/player`) and mandatory `device_id`; added: retry/re-queue on 404/403 — implemented (#159) in `automated_playback.py` (`SpotifyPlaybackClient.resolve_device_id`/`account_is_busy`, `attempt_play`, `TrackSkipped`) and wired into the CLI's `automated-playback --device-name`. Private Session was rejected (client-side toggle, ~6 h expiry, unauditable); all-replay-on-node was rejected (serial node).
- **Parallel clients on one machine need one browser binary per queue** (refining) — per-process loopback captures a process tree, and all of a browser's audio flows through its single audio-service process, so tabs in one browser cannot be separated. Parallel replay on the node therefore maps queues to distinct browsers (e.g. Spotify in Edge, YouTube in Chrome, SoundCloud in Firefox; all in `DEFAULT_BROWSER_APP_STEMS`). The pilot runs one client at a time; per-browser parallelism is the later scaling route.
- **Participants, final (decisions `a278a58b`, `ba589810`)** — three PC-owning friends are all **type A** (Spotify; YouTube Music at ~80/20 phone/PC), running capture during normal listening and replay in idle time (not 24/7 — a ≥3 queue stretches to ~7.5 weeks at ~8 idle h/day, accepted). A fourth person with **no computer at all** (phone only, **Spotify**) is the real **type B**; their Spotify ESH export arrives in ~a month, so the node path is built now and validated first on the owner's own history as a synthetic type B. **Pilot admission requires an exportable multi-year history** — the engine (≥3 filter, temporal roots, epochs, recognition) has no accurate output from install-day capture alone; **SoundCloud has no export and drops out of the pilot** together with its participant. Live capture emitting `ListenEvent`s (`source="live_capture"`) is a post-pilot follow-up (today neither `continuous_capture.py` nor `live_pipeline.py` writes history), not a substitute for history. Load-sharing friends' queues on the node was rejected (trust boundary for a non-critical speedup).

**Post-critic AC lock (2026-09-06; decisions `897224d2`, `2c452a70`, `909d28fe`, `2e17aafa`, `446d7d0a`, `d6c9ffe0`, `45fe71d6`, `9fbaac14`, `87277764`).** Sampling + coverage critics and a grounding pass returned 137 findings; each got a disposition (transcript of session `grill-pilot-fb9dbbd3`). What changed:

- **Slice order is now 0 → 3, schema first.** **Slice 0** (decisions `897224d2`, `2c452a70`, `446d7d0a`): a **timbre root** — `Root.category` gains `"timbre"`, `CategoryWeights.timbre` becomes live, `derive_timbre_clusters` gets a production caller inside RootProfile derivation (reopens `945459ac`; without a consumer, 0 % and 80 % audio coverage yield byte-identical profiles and the replay budget feeds nothing); a **single track-key contract** — the prefixed `canonical_track_id` (`mbid:` > `isrc:` > `spotify:` > `name:`) is the key for audio-analysis files, the pool, history play-counting and queue lookups, and `spotify_track_uri` accepts only `spotify:` keys and fails loudly otherwise (today the live pipeline keys on bare ids, history on bare `spotify_id`, and the backfill "analyzed" check consults SharedStore metadata, so pool dedup would be 0 % effective); the **pool record format** — key + embedding + tags + model version, **no provenance** (timestamps and `app_id` would re-identify participants under serial windows). Refined by #140 (`09cf6008`): an optional track-level `chromaprint_fingerprint` is allowed in the pool record — it identifies the audio, not the participant. **Slice 1** Spotify replay (`2e17aafa`, `909d28fe`): queue selector, driver, capture contract, ledgers. **Queue selector shipped** (#163, `2e17aafa`/`87277764`): `replay_queue.py`'s `select_replay_queue` takes a canonical key with ≥3 valid plays (the same `_is_valid` ≥30s rule as the temporal seed path), drops anything already analyzed (pool or root), and round-robins the remainder across `(artist, year-proxy)` strata up to a cap so no single artist/year can exhaust it — distinct from `select_backfill_tracks`, which builds from the saved library *minus played tracks* rather than from play-count signal. `replay_queue_coverage` computes the AC5.1 stat: share of **valid plays** (not unique tracks) covered by already-analyzed + newly-queued tracks, printed by the `replay-queue` CLI subcommand. No release-year field exists anywhere in the schema, so the stratifier uses a proxy — the *earliest valid play's year* per canonical key — per the "proxy outputs are labelled" invariant below; still outstanding: the driver, capture contract, and ledgers. **Slice 2** Takeout importer + `youtube_id` (`d6c9ffe0`). **Slice 3** node tier + purge (`9fbaac14`).
- **Replay capture contract — shipped** (#166, decision `2e17aafa`) — `replay_capture.py`: capture is armed before the play request; the window starts at the first non-silent frame (RMS ≥ `RMS_SILENCE_THRESHOLD = 0.01`) and lasts `min(track duration, 120 s)` (`DEFAULT_REPLAY_WINDOW_S`), then the driver pauses; a silent or short capture is discarded (no audio-analysis file written) and the track re-queued once (`process_replay_queue`'s `requeue_limit=1`) rather than embedded (today the scheduler advances on wall clock, `read_available` can return short and `_mel_patches` pads to 128 frames, so silence would previously have been stored and first-write-wins dedup would keep it forever); a sample-rate mismatch (`expected_sample_rate`) is journaled and the record discarded. Every attempt is journaled as one JSONL line (`ReplayJournalEntry`: `track_id`, `outcome`, `started_at`, `ended_at`, `reason`) to `<data_root>/replay_journal.jsonl` (`replay_journal_path`); `summarize_replay_journal` and the `replay-journal-summary` CLI subcommand print per-outcome counts for the weekly checkpoint. **Replay identity comes from the queue** (`canonical_track_id` on the `TrackRef`) — SMTC and fingerprinting are bypassed entirely in this path (SMTC prefers a Spotify client over a browser, so it would pick the participant's own Spotify over the replay tab). Refined by #140 (`09cf6008`): replay still runs `fpcalc` on the captured PCM for storage in the pool record (not yet wired), but never for identity.
- **Organic RMS/short gate — shipped** (#179) — `live_pipeline.py`'s `run_live_capture_spike` applies the same gate #166 defines for replay to the organic path: after `track_id` is derived but before the dedup/inference steps, a capture shorter than the requested `duration_s` window or below `RMS_SILENCE_THRESHOLD` (imported from `replay_capture.py`, not redefined) is discarded — `LiveCaptureResult.analysis_path` is `None`, `outcome` is `"short"`/`"silent"`, and no audio-analysis file is written. The discard is journaled as a `ReplayJournalEntry` (same shape as #166's) to `live_capture_journal_path(store)` (`<store.root>/live_capture_journal.jsonl`); `continuous_capture.run_continuous_capture` and both `capture-spike`/`capture-loop` CLI commands default to this path so production runs are journaled, not just tests. Unlike replay, the organic path has no separate window constant — the window *is* the caller's `duration_s`, there being no `DEFAULT_REPLAY_WINDOW_S` equivalent to share.
- **Queue selector** (in `2e17aafa`) — tracks with ≥3 **valid** plays (`_is_valid`, ≥30 s, from `temporal.py`) on the canonical key, minus tracks with an analysis in the pool or root; **not** `select_backfill_tracks`, which excludes played tracks — the inverse of the pilot's queue. The queue is **stratified by artist/year and capped**.
- **AC5.1 is share of valid plays covered, not share of unique tracks** (decision `87277764`, refining `30b40b80`) — HDBSCAN with `min_cluster_size=3` finds structure from a stratified sample, and the 80 %-of-uniques threshold had no stated link to clustering quality; a capped stratified queue fits inside the ~30-day ESH wait. Type A participants request ESH on day 0; the timeline starts at export arrival; a weekly checkpoint reviews the capture journal. Before participants start, a **measurement on the owner's data compares 120 s live-capture embeddings against 30 s windows** (bias vs the models' training clips is unmeasured; follow-up issue).
- **AC3.1 gets an explicit intersection step** (decision `446d7d0a`) — RootProfile derivation reads **pool ∩ participant history**, never the whole pool (`list_audio_analyses` reads a directory; pointed at the pool it would cluster other participants' tracks into every profile). `_group_and_seed` seeding SharedStore during derivation stays: SharedStore is the anonymous track cache by contract and purge does not touch it.
- **Node tier** (decision `9fbaac14`) — `--data-dir` on `desktop_app`/CLI for per-participant roots; a `purge` CLI; the consent file records grantor + timestamp; runbook order **derive → deliver → purge** (no re-derivation after purge); Spotify token stays per data root; `user_id` = root name.
- **Deferred with follow-up issues**: YouTube browser driver and browser-SMTC identity (`d6c9ffe0`); Spotify ToS exposure of automated playback (runbook note). **Resolved by #118 research** (2026-09-06): PANNs/dual embedding and CC BY-NC-ND, formerly deferred at `45fe71d6` — see decisions `b1f30549-7a83-4e2e-82df-e657fe546e72`, `35bc7c5b-bade-44a0-86a7-479967c89e7a`, `24458ec3-eb48-4714-bae3-23f387517f16` below. **Rejected**: Private Session; all replay on node; Spotify relinking handling; per-machine token; n=4 power statement (qualitative pilot).
- **120 s vs 30 s window-bias probe — shipped** (#169, decisions `87277764`, `5a007648`) — `window_probe.py` measures whether the pilot's 120 s capture window shifts embeddings off the MTG models' short-clip training distribution enough to move clusters. **Both legs come from one capture**: the 30 s leg is a front truncation of the same RMS-anchored PCM the 120 s leg embeds, not a second capture, because two captures would vary in content (playback offset, loudness state, loopback conditions) and confound the one variable under measurement — the accepted cost being that the probe measures *no* capture-to-capture variance, so its distances are not a total noise floor (the rendered report says so). It rides on an ordinary replay session through `run_replay_capture`'s additive `on_capture_analyzed` hook (fired only for *accepted* captures, so a discarded silent/short buffer never enters the sample), so its marginal cost is one extra inference pass per track and zero extra replay hours. `compare_cluster_assignments` routes through the production `derive_timbre_clusters` rather than calling HDBSCAN itself — the gate asks whether the *pilot's own* derivation moves — and scores agreement with the adjusted Rand index, labelling each HDBSCAN noise point as its own singleton so two derivations agreeing on nothing but which tracks are noise cannot score a spurious 1.0. Pairs journal to `<data_root>/window_probe.jsonl`; the `window-probe-report` CLI prints the distribution, the ARI and a loud `under-powered sample` warning below `MIN_PROBE_SAMPLE_SIZE = 100` (honest-empty: an unmeasured gate must never read as a passed one).
- **Whole-track vs 30 s stream-decode window-bias probe — shipped** (#201, decision `d4f61147-ec4f-4759-a59f-4684b679c881`) — the 120 s-vs-30 s gate above (#169) only covers the loopback leg; the YouTube stream-decode leg (#170) never captures a fixed window at all, it decodes and embeds the *whole track*, so #201 asks the analogous bias question for that leg with its own journal and CLI command rather than a third comparison point that would blur the two legs' numbers together. It reuses `window_probe.py`'s leg-agnostic machinery unchanged (`WindowPair`, `DistanceSummary`, `ClusterAgreement`, `build_window_probe_report`, `make_window_probe_recorder`) — only `stream_decode_window_probe_path` (a separate `<data_root>/stream_decode_window_probe.jsonl` journal) and generalized `long_label`/`short_label`/`capture_noun` keyword params on `render_window_probe_report` are new. The whole-track leg costs zero extra decode: `make_window_probe_recorder` reuses the decode's own inference embedding, adding only one extra inference pass over a 30 s truncation. The hook is wired in unconditionally on the real CLI entry point, `replay-capture-youtube` (`_cmd_replay_capture_youtube`'s `on_capture_analyzed=`), so the gate rides passively on any real stream-decode pilot session; `stream-decode-window-probe-report` reads the journal back, titled and labelled (`whole-track leg` / `30 s leg`, `#201`) so it can never be mistaken for #169's loopback numbers.
- **Onboarding checklist (runbook)**: see [`docs/pilot-runbook.md`](../pilot-runbook.md) — Windows ≥ 2004 (per-process loopback); Store vs desktop Spotify build; replay browser ≠ daily browser; importer prints skip counts (rows without URI, podcasts).

**Capacity facts that shaped the design** (owner's own ESH, 137,952 plays / 51,409 unique; Zipf simulation for cross-user overlap):
- Replay is 1× realtime ≈ 17 tracks/h. All 51k uniques ≈ 18 weeks 24/7 on one client; the **≥3-plays filter** leaves 12,471 tracks (24% of uniques, 65% of plays) ≈ 4.4 weeks. Single-play tracks carry almost no taste signal, so the filter is the primary throughput lever. Replay-only second lever: advancing after the 120 s capture window ≈ 30 tracks/h, so the ≥3 queue ≈ 2.5 weeks on one client. That 120 s choice is what #169's probe measures, and it is measured **for free**: the probe truncates the buffer the replay path already captured and embedded, so a full-sample (≥100-track) bias measurement adds one inference pass per track and **no** replay hours to the 2.5-week figure — the reason the gate is affordable to run before the pilot rather than deferred past it.
- Cross-user pooling of analysis outputs saves only ~10–45% of replay hours (3% for random-taste pairs, ~40% for 10 very close friends) because long tails don't overlap; pooled unique count grows almost linearly with participants. For type B, none of that work is divisible — it all lands on the node. Parallel clients, not overlap, are the second lever.
- **Actual participants (2026-09-05): three friends, one per service (Spotify, YouTube Music, SoundCloud); two listen 50/50 PC/phone, one has only a work laptop and listens on the phone, i.e. effectively type B.** The 10-participant figure is an aspirational later state. Consequence: with one person per service, the service axis is confounded with the person axis, and cross-user overlap can only be measured between the owner and the Spotify participant.
- Participant services: Spotify, YouTube Music, SoundCloud (Apple Music optional, Yandex Music no longer relevant to the audience). Today only Spotify has a history importer, identity resolution is Spotify-only by design (§Account Data ingestion), and replay exists only via the Spotify API; browser-tab capture for YouTube Music / SoundCloud is expected to work but unverified (§Continuous capture). Service coverage per user type is an open grill item.
