## Backfill playlist & user-OAuth (#127)

The project's **first user-OAuth scope** beyond the existing client-credentials-only Spotify integration. Python: `src/music_intel_mcp/spotify_user_auth.py` (auth) + `src/music_intel_mcp/backfill_playlist.py` (selection/sync logic). Decision `8dd6ef53-2fd3-425d-a8a9-716c23a84d8a`.

- **Grant type: authorization-code + PKCE, no client secret** (`SpotifyUserAuth`) — distinct from the client-credentials flow used elsewhere in the project (ISRC/genre/popularity lookups), which cannot touch a user's library or write playlists.
- **`PLAYLIST_SCOPES = ("user-library-read", "playlist-modify-public", "playlist-modify-private")`.** `user-library-read` is the candidate-pool source (decision `8dd6ef53`: the backfill queue is drawn from the user's *saved/library tracks*, not from listening history — history is consulted only as the AC4 exclusion set, never as the pool itself). `playlist-modify-*` is what lets the feature auto-create/auto-manage the "to-analyze" playlist.
- **Token storage is local-only, never Supabase** (extends decision `f7a9fcbd`'s local-personal-data rule to OAuth tokens specifically) — `SpotifyUserAuth` persists the access/refresh token to `<data root>/spotify_user_token.json`, a plain local file. The shared metadata store stays anonymous track-level facts only; a user's OAuth token is exactly the kind of personal credential that invariant exists to keep off the cloud.
- **Opt-in gate:** `MUSIC_INTEL_BACKFILL_PLAYLIST_ENABLED` (env var, documented in `.env.example`) — the feature is off by default because it writes to the user's real Spotify account. `is_backfill_enabled()` is checked before anything else in the `backfill-playlist` CLI command.
- **Two new CLI commands** (`cli.py`):
  - `music-intel spotify-login` — one-time interactive authorization: builds the PKCE challenge + authorize URL, runs a local loopback HTTP server (`_wait_for_oauth_callback`) to catch the redirect, validates the `state` param (anti-CSRF), and exchanges the code for a token via `SpotifyUserAuth.exchange_code`.
  - `music-intel backfill-playlist` — the daily-refresh sync: gate check → auth check → fetch saved tracks (candidate pool) → exclude played (AC4) and already-analyzed (AC3, via `UserStore.has_audio_analysis` keyed by the single `canonical_track_id` contract — see #158, decision `2c452a70`; the original #126 `SharedStore`-metadata-presence check this replaced had no embedding at all and never agreed with the live pipeline's key) → cap at `MAX_BACKFILL_TRACKS=10_000` (AC2) → diff against current playlist membership and apply add/remove (AC1).
- **AC3's removal is membership-diff, not a special "remove" path** — `diff_playlist_membership` just computes desired-vs-current on every run; a track that gained an analyzed entry since the last sync simply drops out of the desired set and gets removed on the next refresh, same code path as normal churn.
- **AC2's daily cadence is a local continuous-loop CLI flag, not a GitHub Actions cron.** Rejected cron because the OAuth token lives in `<data root>/spotify_user_token.json` — local-only, per the token-storage decision above — and a GitHub-Actions-hosted job has no access to that file. Instead `backfill-playlist --loop [--interval-hours N]` (default 24h) wires `run_continuous_backfill` (`backfill_playlist.py`), which mirrors `continuous_capture.run_continuous_capture`'s injectable `stop_event`/`sleep` convention: `while not stop_event.is_set(): sync_once(); sleep(interval_s)`, with `on_result`/`on_error` callbacks so a single failed sync cycle is reported and skipped rather than killing the loop. Default (no `--loop`) behavior is unchanged — a single sync-and-exit run, e.g. for a user-scheduled Task Scheduler entry instead.
