## YouTube Music stream-decode capture + browser SMTC identity (#170, grill 2026-09-07)

**Why this section exists.** The pilot deferred the YouTube branch of replay (decision `d6c9ffe0`); this grill designs it. Replay is the only audio source for a Takeout-history participant's phone-time listening. The grill's central pivot (decision `6c9144ea-f93e-46de-b13e-7a4bc4af3169`): the branch no longer *plays* anything — it **decodes the stream directly**, so the browser-URL replay driver designed in the first half of this session is withdrawn, and **#166 is no longer a blocker** (decision `20c86c53-2c29-48f7-8f6d-68a297654d1b`). The identity half of the section — the history-backed `youtube` rung and its alias plumbing (Q2) — survives unchanged, because it belongs to *organic* capture, not to replay. Q3 (how a `youtube:` key meets `mbid:`/`spotify:`) is owned by §Near-duplicate key reconciliation (aliases + `resolve_key`, prefix rank `mbid:` > `isrc:` > `spotify:` > `youtube:` > `name:`); history-only `youtube:` keys with no embedding go through #178.

- **Capture by stream decode, not by playback** (decision `6c9144ea-f93e-46de-b13e-7a4bc4af3169`) — the YouTube branch obtains PCM from a yt-dlp-class extractor and feeds it straight to `run_inference`; no browser, no window, no realtime pacing. This **supersedes decisions `48f764b9` (CDP page-observing driver), `792fbc97` (watch page over the Music SPA), `b8f58c08` (ad policy, Q1) and `3283034f` (driver mechanics)** — all four were mechanisms for controlling and observing a page that no longer exists in the design. Q1 is answered by dissolution: an extracted stream carries no ads, so there is no ad/autoplay bleed to police and no Premium profile to keep signed in. The pilot's output is a timbre embedding, not a listening event, so playback was never the goal; decode runs far above realtime, which is what makes the queue cap and the >=3-play threshold negotiable rather than economically fixed.
- **Extraction shape** (decision `29743073-4876-4b06-a44a-880a498470e0`) — decode runs **locally on the participant's machine**, beside the desktop app, never on a node. The extractor is **`yt-dlp` as an optional dependency behind a `Protocol` seam**, never vendored, so the volatile part stays a pinned third-party package the participant can upgrade independently and the branch degrades to "unavailable" rather than breaking when it is absent. The decoder emits a **stereo `AudioFrame`** and **never downmixes at the seam** — `_mel_patches` collapses to mono at 16 kHz for Discogs-EffNet, but that is the model backend's business, not the capture contract's.
- **#166 is not a blocker** (decision `20c86c53-2c29-48f7-8f6d-68a297654d1b`) — the replay capture contract's acoustic-window mechanics (arm-before-play, signal-anchored `min(duration, 120 s)` window, RMS/short-capture re-queue) exist to bound a *live* acoustic capture and have no meaning for a decoded file. Only the contract's **per-track JSONL journal** carries over as the branch's outcome record.
- **`unavailable` is its own journal outcome** (decision `f7aa8da7-1ce9-4c97-825b-3e35cad07d64`; source reworded by `6c9144ea`) — removed, private and region-locked videos are journaled `unavailable`, abandoned without re-queue, and counted separately in the weekly checkpoint. The signal is now an **extractor error**, not a CDP `playabilityStatus` read. They are the leak AC5.1 (decision `87277764`) exists to measure; folding them into `silent` would hide it inside capture-failure noise.
- **Metadata cross-walk before any decode** (decision `1ffb5614-1cd6-4109-966e-d300a54ddc47`) — a track's `youtube:` key is first walked to `isrc:`/`mbid:` and checked against the pool, so an embedding that already exists satisfies coverage with **no capture at all**. The bridge is the existing `resolve_mbid` seam on the queue selector (`select_replay_queue`), not a new mechanism.
- **Coverage ceiling is measured before it is bound** (decision `c3ffbb76-1728-42e0-8eca-6597db225eb7`) — the >=80 % valid-play criterion (AC5.1, decision `87277764`) is not applied to the YouTube participant until the achievable ceiling has been measured on their real imported history. The denominator holds *all* valid plays while the numerator only ever holds >=3-play tracks capped at 200, and Takeout carries no duration — so `_is_valid` counts every skip as a valid play for this participant while a Spotify participant's sub-30 s plays are filtered out. The same measurement decides whether `MIN_VALID_PLAYS` and `DEFAULT_REPLAY_QUEUE_CAP` are lifted for this branch.
- **History-backed `youtube` rung for organic capture (Q2)** (decision `02b7aff6-c05d-4988-8d4b-7bbeb7ede77d`) — `LiveIdentityResolver` gains a rung **after MB name search and before the normalized name key**: a local index `(normalized title, normalized artist) → youtube_id` built from the participant's own imported Takeout history, yielding a `youtube:<id>` identity above name level, so the `_is_resolvable` admission gate (#145) admits the capture unchanged. A normalized key that maps to more than one id resolves to nothing (fragmentation over false merge). When the fingerprint rung also wins an MBID for the same capture, the pipeline emits an alias `youtube:<id> → mbid:…` so the history key resolves through `resolve_key` (landing site refined below: participant root, decision `661b6e10`). Rationale: for a Takeout-history participant every organic capture was dead weight — admitted only via Spotify search, pooled under `spotify:`/`mbid:`, and never joined to their `youtube:` history until #140 had both sides embedded, i.e. after the replay it should have saved. Admitting all name-level browser candidates was rejected as reopening #145.
- **History-rung mechanics** (decision `e418b7fb-95f5-4fb2-9c1f-f3df39697f3f`) — the index is built in `_build_live_resolver` from the participant root's imported events carrying `youtube_id`, in memory per process, as a new source matching the existing rung `Protocol`s; `None` when no Takeout history exists (rung inert). The SMTC-side artist has the `" - Topic"` channel suffix stripped with the importer's constant before `normalize_track_name`, so both sides of the index agree. Assumption carried into implementation: Chrome forwards YouTube's MediaSession metadata to SMTC.
- **Alias lands in the participant root, not the pool** (decision `661b6e10-627b-4d63-8a59-b6e3417b4b19`, refining `02b7aff6`) — the waterfall stops at the deepest winning rung, so the pipeline queries the history index as a **side lookup regardless of level**; when the winning level is deeper than youtube and the lookup is unique it appends `youtube:<id> → <winner>` with tier **`history_title_match`** to the **participant root's** aliases file. A title match is weaker than #140's fingerprint/embedding tiers and is derived from one participant's history, so it never crosses participants through the pool aliases file. It still does its job because the participant's own reads (queue selector, pool ∩ history) resolve their history keys through the participant-root aliases before comparing with the pool.
- **Alias emission is gated on score-backed evidence** (decision `4c0041b5-cb93-4106-a92a-fcc03fb8ba41`, refining `661b6e10`) — the organic path writes the `youtube:<id> → <winner>` alias **only when the winning rung is score-gated evidence** (AcoustID / ISRC / MBID). A win at `spotify_search` or `mb_name` journals the near-miss and writes no alias: neither rung is score-gated (`live_identity.py` gates AcoustID on `min_acoustid_score` but takes the first Spotify search hit unconditionally), so composing an unscored title match with an unscored search hit would let two independent guesses mint a permanent alias line.
- **`resolve_key` reads a chain** (decision `7a40049d-52ba-4d33-97de-c11ba45506c5`, refining `0b0de476`) — with a participant-root aliases file in play, `resolve_key` takes an **ordered chain** of alias files, participant root first then pool, with one cycle guard spanning both. The queue selector, the pool ∩ history intersection and `has_audio_analysis` resolve a participant's history keys through that chain before comparing with pool keys; the offline near-dup job that maintains the pool never reads participant alias files.
- **Accepted costs, recorded not resolved** — a public repository shipping a YouTube stream extractor (an owner values call, not a technical one), and an unquantified **capture-path skew** between decoded PCM and WASAPI loopback PCM in a pool that carries no provenance. Two findings were scoped out of #170 and filed separately (#193, #194): stereo as a clustering signal (it cannot ride inside a mono-16 kHz EffNet embedding, so it is a pool-schema change), and the un-normalized `log10(1 + _MEL_LOG_SCALE * mel)` input that makes embeddings depend on playback volume on the organic path. `RingBufferSink` never persists audio, so both are backfillable **only** on the decode branch — a decoded track can be re-decoded from its stored video id; an organically captured one is gone.
