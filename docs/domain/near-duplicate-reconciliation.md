## Near-duplicate key reconciliation — offline embedding-space batch merge (#140, grill 2026-09-06)

**Why this section exists.** Under the pilot, three key sources meet in one anonymous pool: organic capture yields `mbid:` (AcoustID) or `name:`, replay takes identity from the queue (batch waterfall → `mbid:` via the ISRC index or `spotify:`), and the Takeout importer adds `youtube:`. The same recording therefore lands under two or three canonical keys, while `has_audio_analysis`, the replay queue selector and the pool ∩ history intersection compare keys literally. #140 is the pilot's **key-reconciliation mechanism** (decision `fa49f130-4592-4c49-a16f-fc77eb2d8500`); it sits in milestone *Multi-user pilot* after #161. Terms:

- **Near-duplicate job** — an offline batch that scans one `audio_analysis/` directory (the node pool or a participant root), generates candidate pairs from embedding distance, checks each pair against any available fingerprints, and writes a **report**; it never merges on its own. Its honest benefit is **alias accumulation across participants** — a confirmed alias makes a later participant's history key "already analysed" — not replay-hour savings within one run (embedding candidates exist only after both sides were analysed).
- **Evidence tier** (decision `09cf6008-013f-4017-a70c-36ae3bb2eae9`) — every proposal is tagged `fingerprint+embedding` (both records carry a chromaprint fingerprint and the offline comparison agrees) or `embedding_only` (a fallback held to a stricter distance threshold). To make the first tier reachable in the pool, the **pool record gains an optional track-level `chromaprint_fingerprint`** (refining `446d7d0a`: its no-provenance rule targets `captured_at`/`app_id`, which re-identify participants; a fingerprint identifies the audio, not the person) and **replay computes `fpcalc` on the captured PCM after the RMS gate, for storage only** (refining `2e17aafa`: identity still comes from the queue; no fingerprint-based identity lookup happens in replay).
- **Alias** (decision `0b0de476-9988-4f86-8cad-639388215894`) — an accepted merge is one `loser_key → winner_key` line in an aliases file beside the `audio_analysis/` directory. Analysis files are never deleted or rewritten (first-write-wins stays intact; un-merge = delete the line). One `resolve_key` helper is honoured by `has_audio_analysis`, the queue selector and the pool ∩ history intersection. Listening history is never rewritten; the alias file is the designed input for a future history-remap job.
- **Offline fingerprint comparison** (decision `58ddb957-f93a-4a76-991a-659e11cb7b45`, superseding `dba5444a`) — no decoder: `fpcalc -raw -json` is invoked a second time on the same wav and the **raw uint32 array** is what the pool record stores in `chromaprint_fingerprint`; the participant sidecar keeps the compressed string for AcoustID. Records without a raw array fall to `embedding_only`. AcoustID re-query is rejected (live API; repeats the lookup that already failed at capture time for exactly the `name:` records).
- **Mechanics** (decision `de04cfa6-1dee-42b8-a4bc-10058ab6440c`) — candidates: cosine over L2-normalised raw embeddings (same space as timbre clustering), chunked brute force, top-5 per record. Match: best offset within ±len/2 frames, bit-error-rate ≤ 0.25 over ≥ 240 overlapping frames (~30 s) — named constants, printed in the report. Winner: prefix rank `mbid:` > `isrc:` > `spotify:` > `youtube:` > `name:`, tie → lexicographically smaller key; mtimes never consulted. `resolve_key` follows chains with a cycle guard; `apply` canonicalises to the final winner. Report: `<root>/near_dup/report-<ts>.json` + `.md`, one entry per considered pair (keys, distance, tier, fingerprint `{ber, offset, overlap}` or null, verdict, reason, `accepted: null`); rejection reasons `above_threshold` / `fingerprint_disagree` / `already_aliased` / `same_key`. `apply` reads only `accepted: true`, no `--all`, idempotent. `aliases.jsonl` holds `{loser, winner, tier}` — no timestamp, no report id (merge time correlates with participant windows). Pool reports carry no titles.
- **Report + apply** (decision `c8e2aa66-4401-40f8-bdee-6f5815e50c4e`) — the job emits a report artifact (JSON plus a readable rendering) listing every considered pair with its distance, fingerprint result, tier and verdict, including pairs rejected and why (transparent rejection). A separate `apply` step consumes the reviewed report and writes aliases only. No interactive loop, no silent auto-merge.
- **Post-CRITIC refinements** (decision `43f06eb2-51c1-47a2-b965-1394d79bda2e`) — raw arrays are computed by **both** organic capture and replay (one temp wav, two `fpcalc` calls) and live in a **`fingerprints/<key>.json` sidecar directory** beside `audio_analysis/`, not inside the pool record (refining `09cf6008`/`58ddb957`: #161's exact schema stays, write-once records can be back-filled, no field-type overload with the participant sidecar's compressed string). **Hub guard**: a record with ≥ N neighbours at distance ≈ 0 (silence/ad captures mean-pool to one vector) is `hub_suspect` and all its pairs are rejected. **Alias precedence**: pool aliases win, participant-root aliases apply only inside that root, disagreements are reported as `alias_conflict`. **Pilot scope**: the job's leverage is the organic (`mbid:`/`name:`) vs replay (`spotify:`) pair; `youtube:` in the pool is post-pilot (#170); history-only keys with no embedding are out of reach and go to the metadata cross-walk (#178); the organic RMS gate shipped in #179 (reuses `RMS_SILENCE_THRESHOLD`, see above). Rejected: timestamps/report ids on alias lines (report on the node is the audit trail); a pure-Python chromaprint decoder.
- **Thresholds are constants** (decision `bdb3c02a-fdfa-4683-85b2-fb455d0ebd3c`) — no records exist on disk yet, so the distance thresholds ship as conservative constants; the report shows every distance so calibration becomes a follow-up issue once a real pool exists.
- **Implementation-time scope narrowing (#140 PR)** — the grilled design above is broader than what one PR wires end-to-end; these decisions record where the implementation stopped short of the full design and why, without changing the design itself:
  - Overall PR scope (decision `f78fcb30-da74-43b3-827d-68078a302f05`) — this PR covers the raw chromaprint sidecar (`fingerprints/`), the `near-dup scan`/`apply` CLI, `aliases.jsonl`, and `resolve_key` wired into `has_audio_analysis` only; the queue selector, pool ∩ history intersection, and pool-vs-participant alias precedence are follow-up work.
  - Replay-side fingerprint sidecar (decision `39078a7b-5b74-4250-9a75-80851953c04a`) — `fpcalc -raw -json` → the `fingerprints/<key>.json` sidecar is wired only into the organic capture path (`live_pipeline.py`); `automated_playback.py`'s replay path does not compute a raw fingerprint in this PR, narrowing AC1 from "both organic capture and replay" to organic-only for now.
  - `resolve_key`/`has_audio_analysis`-only wiring (decision `ce94e03c-acf1-4533-99cf-2fbbca36b3c4`) — `resolve_key` is called from `UserStore.has_audio_analysis` only; the replay queue selector (`select_backfill_tracks`) inherits alias-awareness transitively through that same call (both `cli.py` call sites pass `store.has_audio_analysis` directly), but `played_track_ids()`'s exclusion-set computation does not resolve aliases directly.
  - `near_dup.py` has no pool/participant duality (decision `babd708d-3e38-414b-aab2-edf39a5e06f7`) — `scan()`/`apply()` operate on a single literal `UserStore` root; there is no separate pool-root concept inside `near_dup.py` yet, so the "pool aliases win over participant-root aliases" precedence rule above is not exercised by this PR's code (it's already implemented at the `resolve_key(pool_aliases, root_aliases)` layer in `store.py`, just not fed two distinct roots from `near_dup.py`).
  - `already_aliased`/`same_key`/`alias_conflict` reasons deferred (decision `0dc8b584-1fe9-4346-bf94-a22dfb54c079`) — the rejection-reason enum above lists `already_aliased`/`same_key`, and the precedence bullet above names `alias_conflict`; none of #140's six AC checkboxes require emitting them, `same_key` is structurally unreachable given one record per distinct key, `already_aliased` is a low-cost gap because `apply` is idempotent, and `alias_conflict` needs the pool/participant duality that decision `babd708d` above scoped out of this PR.
