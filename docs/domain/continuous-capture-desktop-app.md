## Continuous capture loop + distributable desktop app (#136)

Turns the #124 spike (one shot per manual invocation) into an unattended collector any non-technical user can run indefinitely, so the audio-decomposition embedding corpus (§`0c762eec`) can start filling from real listening sessions beyond the owner's own machine.

- **`capture_factory` is a factory, not a fixed instance** (`continuous_capture.py`). The real WASAPI backend needs the resolved `process_id` at construction, and the PID can change between tracks even for the same app — a fixed instance couldn't survive a track change.
- **`desktop_app.py` constructs its own resolver/store rather than reusing `cli.py`'s `_build_resolver`.** That helper is `argparse.Namespace`-coupled and private; the desktop app has no namespace to hand it, and reaching across a `_`-prefixed CLI internal would be the wrong coupling direction. Both entry points (CLI `capture-loop` subcommand and the tray app) wrap the same `run_continuous_capture`.
- **Multi-source support required no new code.** Windows SMTC (the `NowPlayingSource` backend) and per-process WASAPI loopback are both OS-level and app-agnostic by design — a YouTube Music or SoundCloud tab exposes now-playing info via the browser's Media Session API → SMTC integration, same as any native app. This is expected to just work; **not yet empirically verified** against a live browser-playback session (verification, not new engineering, is the remaining gap).
- **No redistribution of the MTG ONNX models.** The setup path (`scripts/setup_collector.ps1`, `docs/COLLECTOR_SETUP.md`) never bundles or downloads the licensed `.onnx` files on the user's behalf — they fetch `discogs-effnet-bsdynamic-1` and `mtg_jamendo_top50tags-discogs-effnet-1` (`.onnx` + `.json` sidecar each) themselves from essentia.upf.edu into `.scratch/models/`. The ND clause governs the model files themselves, so redistributing them stays off-limits. It does **not** govern their *outputs*: MTG confirmed on 2026-09-15 that per-track activations and embeddings fall outside the licence's no-derivatives scope (decision `ad39cbcd-035c-487d-94eb-04c6f3ea081e`, superseding the local-only-outputs reading of `29852699`).
- **Prebuilt `.exe` distribution deliberately deferred.** Users without VS2022/Build Tools currently cannot build the native WASAPI helper. Publishing a prebuilt binary as a GitHub Release asset would remove that requirement but is a public, outbound-facing action — deferred as a fast-follow pending explicit go-ahead, not attempted silently.
- **Loud, fail-fast model-file resolution (#160 AC1).** `inference.py`'s `_resolve_model_path` raises `ModelFileNotFoundError` immediately — naming the resolved path and how to configure it — when neither an explicit path, the env var, nor the `.scratch/models/` default-filename fallback resolves to an existing file. Inference must refuse to start rather than silently degrading; there is no partial result to fall back to.
- **RSS ceiling breach is the one exception to isolate-and-continue (#160 AC2).** `check_rss_ceiling` (`inference.py`) is called after each successful per-track inference in `run_continuous_capture`; unlike every other per-track failure (isolated via the generic `except Exception` and journaled through `on_error` while the loop keeps polling — see above), a raised `RssCeilingExceededError` is journaled via `on_error` and then the loop *returns* — sustained memory growth past the ceiling is a signal to stop the session, not a per-track fluke. `rss_reader` is an injectable `Callable[[], float]` seam (default reads `psutil`) so tests never need `psutil` importable or monkeypatched.
- **One shared `PEAK_RSS_CEILING_MB` constant, not two (#160 AC3).** Defined once in `inference.py` and imported by `scripts/benchmark_onnx_engine.py`; `test_peak_rss_ceiling_mb_is_shared_with_inference_module` asserts `is`-identity, not just equality, to catch an independently-redefined literal drifting apart from the runtime value.
- **Low-memory ONNX session options close the #160 AC3 RSS gap (#175).** The `peak_rss=2467.5MB` recorded in commit `977a7da0` (~65% over the 1500MB ceiling) traced to `onnxruntime`'s default CPU memory arena (`enable_cpu_mem_arena=True`) pre-allocating and retaining large blocks per session — this chain runs one track at a time, so it never gets the batching benefit the arena exists for. `inference.py`'s `low_memory_onnx_session_options()` (disables `enable_cpu_mem_arena` and `enable_mem_pattern`) is the single shared `SessionOptions` construction used by both production (`DiscogsEffnetOnnxModel`/`MtgJamendoClassifier` `_ensure_session`) and `scripts/benchmark_onnx_engine.py`'s `build_sessions()` — mirroring the `PEAK_RSS_CEILING_MB` single-constant invariant above, so the two call sites can't independently drift. A re-measured benchmark run under the fixed config: `peak_rss=894.6MB`, `p95=2.069s` (latency unchanged from baseline) — verdict **SUSTAINABLE**, comfortably under the ceiling. The ceiling itself did not need raising.
- **`get_sessions()` enumeration + app-id allowlist + resolvability-gated browser admission (#138), decision `fbb98b8e`.** `SmtcNowPlayingSource.current()` no longer trusts `get_current_session()`'s single-session guess — it enumerates every SMTC session (`get_sessions()`) so a music session playing behind a non-media foreground app is still found. Each candidate is classified by its AUMID "stem" (`nowplaying._classify_app`, same normalization as `_process_id_for_app`) against `DEFAULT_SPOTIFY_APP_STEM`/`DEFAULT_BROWSER_APP_STEMS`; anything outside {Spotify} ∪ {known browsers} is dropped unconditionally. A literal allowlist alone can't fix browser playback, though: a browser tab's `source_app_user_model_id` is the browser's own AUMID (e.g. `chrome.exe`), not the site/service, so it can't tell a YouTube Music tab from a podcast or call tab in the same browser. The fix is **resolvability-gated admission** (`nowplaying._is_resolvable`): a browser candidate is only admitted if its track resolves through the identity waterfall to something more specific than a bare `"name"` match — this is why `SmtcNowPlayingSource.__init__` now requires `identity_resolver` (breaking change; all 3 call sites — `desktop_app.py`, `cli.py` `capture-spike`/`capture-loop` — updated). Selection across multiple simultaneously-`Playing` allowlisted candidates (`nowplaying._select_now_playing`) deterministically prefers Spotify, else the first `Playing` candidate in enumeration order — SMTC exposes no reliable recency/activity timestamp, so no recency heuristic is used.
- **Gate rewired onto the live waterfall (#145), decision `ac7982aa`.** #138's own note above ("the admission bar tightens automatically once #139's identity waterfall lands") turned out to require an explicit code change nobody made in #142/#143: `_is_resolvable` still called the batch `IdentityResolver` (spotify_id→ISRC→MBID only, no text search), so browser tracks with no prior `spotify_id` (e.g. SoundCloud in Edge) were unconditionally dropped even after #139 shipped. Fixed by having `_is_resolvable` call the same `LiveIdentityResolver` instance already constructed for post-capture resolution (`resolve(title=..., artist=..., fingerprint=None)`) — its AcoustID rung is a no-op pre-capture (no PCM yet, hence `fingerprint=None`), but the `mb_name`/`name` text rungs work unchanged, giving browser candidates a real shot at resolving above bare-`name`. Because this gate runs on every 5s poll (not once per track), `SmtcNowPlayingSource` now keeps a **session-lifetime in-process admission memo** keyed by `(title, artist, app_id)` — mirroring `continuous_capture.py`'s existing `_track_key` pattern — so the waterfall is only actually walked once per unique track per session, not once per poll (protects the project's "external APIs cost money, cache aggressively" rule). Rejected browser candidates are recorded to a JSONL drop-breadcrumb at `<data root>/smtc_drops.jsonl` (`nowplaying.DEFAULT_DROP_LOG_FILENAME`, overridable via `SmtcNowPlayingSource(drop_log_path=...)`) — transparent-rejection, not silent-drop. `nowplaying.resolve_now_playing()` (a separate, test-only free function for unrelated batch resolution) is explicitly untouched — confirmed by a CRITIC pass before AC-lock that it shares a same-named `resolver` parameter with the gate by coincidence, not by design relationship. **Today's real-world effect**: Spotify sessions still admit immediately; browser sessions now admit whenever SMTC title/artist resolves via MusicBrainz name search, closing the gap #138 predicted but never wired.
