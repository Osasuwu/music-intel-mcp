## Shared-store schema (V0)

The shared metadata store (Supabase Postgres) holds **anonymous track-level facts only** — no `user_id`, no `played_at`, no play-context in any table. Migration: `supabase/migrations/20260609000000_shared_metadata.sql`. Python client: `src/music_intel_mcp/shared_store.py`. Issue #60, decision `f7a9fcbd`.

Tables:

- **`tracks`** — canonical identity + denormalised display facts. PK is a **canonical string id** (`mbid:…` > `isrc:…` > `spotify:…` > `name:<casefold>\x1f<casefold>`), built by `canonical_track_id()` — the same waterfall #61 formalises. Columns: `id`, `spotify_id`, `isrc`, `mbid`, `name`, `artist`, `artist_id`→artists, `fetched_at` (TTL anchor). Indexed on spotify_id/isrc/mbid for the identity waterfall.

**Single track-key contract (#158, decision `2c452a70`).** This same prefixed `canonical_track_id` is the *one* key used everywhere a track needs identifying, not just in this table: audio-analysis file names and `UserStore.has_audio_analysis` / `write_audio_analysis` / `list_audio_analyses`, history play-counting, and the backfill/automated-playback "already analyzed" check all derive it from the same function — previously the live pipeline keyed on a bare id, history on a bare `spotify_id`, and the "analyzed" check consulted SharedStore metadata presence (which has no embedding at all), so a pool lookup keyed one way and a history key built the other way never met and cross-participant dedup was 0% effective. `spotify_track_uri` now accepts only `spotify:`-prefixed keys and raises `ValueError` on anything else (a bare id, or an `mbid:`/`isrc:`/`name:` key, would otherwise be silently mangled into a bogus Spotify URI). Pre-existing bare-key audio-analysis files are converted in place by the one-shot `migrate-audio-analysis-keys` CLI (`music_intel_mcp.cli`) — idempotent rename, first-write-wins on a conflicting target, conflicts reported rather than overwritten.
- **`artists`** — artist-level facts (`mbid`, `name`). Defined for #61 + future artist enrichment; V0's `TrackMetadataRecord` denormalises `artist` onto `tracks` and does not yet populate this table.
- **`audio_features`** — one row per track (PK = `track_id`): `bpm`, `energy`, `valence`, `danceability`, `acousticness`, `instrumentalness`, `source`. All nullable (partial enrichment is valid).
- **`tags`** — many rows per track: `(track_id, tag, weight, source)`, unique on `(track_id, tag, source)`. Scene/cultural tags from Last.fm etc.

`TrackMetadataRecord` (pydantic, `extra="forbid"`) is the **pull unit** — a track's `tracks` row + its `audio_features` + its `tags`, plus `fetched_at`. `extra="forbid"` is the structural guard that personal data can never leak into a shared-store record.

**Store access** is `SharedStore` (Protocol) with only **bulk** ops — `get_tracks(ids)` / `upsert_tracks(records)`; no singular getter exists, so the no-round-trip rule is enforced by the type. Implementations: `LocalSharedStore` (**V0 default** — file-backed JSONL persistent cache, atomic temp-file + `os.replace` rewrite, resumable, last-line-wins), `InMemorySharedStore` (ephemeral; real store in tests + offline fallback), and `SupabaseSharedStore` (network-only, lazy-imports the `supabase` optional extra, never run in CI). **The Postgres tables above are the deferred V2+ target — see decision `813de040`:** at single-user V0 the shared store's only edge (cross-user cache sharing) is nil, so V0 persists to the local JSONL and keeps Supabase as a flag-flip (`--shared-store supabase`) for when multi-user lands. `pull_and_cache(ids, store, cache, now, ttl_days=90)` serves fresh entries from the local `MetadataCache` (`data/cache/`), collects uncached/stale ids, and fetches them in **one** bulk call; stale (past-TTL) store entries are surfaced for re-enrichment, missing ids for enrichment.
