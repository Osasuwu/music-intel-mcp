## Live capture pipeline (#124 spike — WASAPI loopback → librosa/onnxruntime)

The first concrete slice of the audio-decomposition milestone (#109, see decisions `3ca7565c`/`16d7f570`/`1c0f37f0`/`29852699` below): a **live** capture pipeline, architecturally distinct from and complementary to the existing **offline batch** audio root pipeline (§Audio root pipeline, which joins pre-computed AcousticBrainz features by MBID). This one runs the MTG models itself, in real time, against whatever the user is playing right now.

- **Native-helper + subprocess IPC, not in-process COM (root-cause finding).** WASAPI per-process loopback activation (`AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`) delivers its `ActivateCompleted` callback via genuine **out-of-process RPC from audiosrv** — comtypes never receives that callback for this specific activation type, even though the same call succeeds outside comtypes/Python (root-caused via a hand-rolled native repro, not assumed). `src/music_intel_mcp/_wasapi_loopback.py` therefore spawns a small compiled C++ helper (`native/wasapi_loopback_helper/main.cpp`, built by `scripts/build_wasapi_helper.ps1`, gitignored `.exe`/`.obj`/`.pdb`/`.ilk` — source only in git) that performs activation and capture natively and streams raw interleaved 16-bit PCM back over its stdout pipe. Wire protocol: one 16-byte header (`status, sample_rate, channels, bits_per_sample`, little-endian uint32 each — `status==0` success, nonzero is an HRESULT or `0xFFFFFFFF` for activation-timeout) followed by the continuous PCM stream. Python's `_StreamReader` pumps the pipe into a lock-protected in-memory `bytearray` on a background thread — the helper never touches disk and neither does the Python side (AC2: audio never persisted).
- **AUMID/ancestor-tree PID resolution (`nowplaying._process_id_for_app`).** SMTC's `SourceAppUserModelId` doesn't map 1:1 onto a process name (`SpotifyAB.SpotifyMusic_zpdnekdrzrea0!Spotify` vs `Spotify.exe`) or onto a single PID (UWP-packaged apps run as several sibling processes). Resolution strips the `.exe` suffix for matching, then among same-named matches walks each candidate's parent chain and picks the **ancestor-most** one — this maximizes coverage for `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE`, which captures a process and its descendants (a child-process PID would miss its own parent's output). No match → `None`, and the pipeline exits early rather than guessing (`live_pipeline.run_live_capture_spike` returns `None` when nothing is playing or no PID resolves).
- **Pipeline DI seam.** `live_pipeline.run_live_capture_spike(*, duration_s, now_playing_source, identity_resolver, capture, embedding_model, classifier, store) -> LiveCaptureResult | None` orchestrates `resolve_now_playing()` → `capture.start()`/`read()`/`stop()` → in-memory `RingBufferSink` → `run_inference()` → `store.write_audio_analysis()`. Every dependency is a Protocol seam (`NowPlayingSource`, `IdentityResolver`, `LoopbackSource`, `AudioEmbeddingModel`, `ClassifierModel`, `UserStore`), unit-tested with fakes; the real implementations (`SmtcNowPlayingSource`, `WasapiProcessLoopbackCapture`, `DiscogsEffnetOnnxModel`/`MtgJamendoClassifier` via onnxruntime resolving `.onnx` files from `.scratch/models/`, `UserStore`) are exercised only by the gitignored manual smoke script `.scratch/live_full_pipeline_test.py`, not the automated suite — hardware/COM/subprocess integration is not fake-mockable in a meaningful way, so it is verified by a real playback run instead (AC3/AC4 verified this way: real embedding + classifier tags produced, identity matched SMTC exactly).
- **Local-store-only write (AC5).** `UserStore.write_audio_analysis()` writes JSON under `<root>/audio_analysis/<safe_name>.json` — there is no Supabase code path in this write; the constraint is structural (the class has no cloud client), not a convention that could be silently bypassed. `<safe_name>` is derived from `canonical_track_id()` (#158 AC1) — the pipeline builds a `TrackRef` from the resolved identity and runs it through the same waterfall the shared store uses, not an ad-hoc `mbid or spotify_id or isrc or name_key` chain — so a track captured live is keyed identically to how the pool, history counting, and the backfill "analyzed" check key it. Audio-analysis files written before #158 under a bare id are converted in place by the one-shot `migrate-audio-analysis-keys` CLI (#158 AC4).
- **Verified against live hardware, not just fakes.** Unit tests (`tests/test_wasapi_loopback.py`, `tests/test_nowplaying.py`) mock `subprocess.Popen`/`psutil` entirely and cover header-parsing, HRESULT/timeout/format-mismatch errors, PCM→float32 conversion, and AUMID/ancestor-tree PID resolution. All five #124 acceptance criteria were additionally confirmed against one live playback session (per-process isolation, no disk writes, real embedding+tags produced end-to-end, identity match, local-only write) — see the manual smoke script above.
