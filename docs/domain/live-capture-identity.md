## Live-capture identity & session selection (#139)

A **second, separate** identity waterfall for the live-capture path (#124/#136's continuous WASAPI loopback capture), sibling to — not a replacement for — the batch/history waterfall above. Python: `src/music_intel_mcp/live_identity.py`. `canonical_track_id()` and every existing stored cache key are **untouched**; this module never writes into the batch `IdentityCache`.

- **Capture-then-identify ordering (AC1).** #124's original spike resolved identity *before* capturing; #139 inverts this: `run_live_capture_spike` (`live_pipeline.py`) now captures the ~120s of PCM first, computes the chromaprint fingerprint from the captured audio (`chromaprint_fpcalc.py`, shells out to `fpcalc -json`), and only then calls `LiveIdentityResolver.resolve()` with that fingerprint. Fingerprinting failure is **non-fatal** — wrapped in try/except in `live_pipeline.py` — and simply drops the AcoustID rung, falling through to the string chain (this is what AC3's fragmentation bias requires structurally, not just at the score-threshold level).
- **Waterfall order (AC2/AC3), deepest rung wins:** AcoustID fingerprint (high-score match only) → Spotify search → ISRC (via Spotify) → MBID (via MB ISRC index) → MB name search → normalized name key. The reached rung is recorded on `ResolvedIdentity.level`. A low-score AcoustID match is treated as a non-match and falls through — **fragmentation over false merge** is the deliberate bias (mirrors the batch waterfall's `2b262dc9` name-rung caution, applied here to the fingerprint rung instead).
- **Credential-gated rung construction (production wiring decision, this issue).** `LiveIdentityResolver.resolve()` has no internal try/except around its rung sources — a missing-credential `RuntimeError` from e.g. `AcoustIdApiSource` would propagate uncaught. Rather than adding exception handling at each call site, `cli.py`'s and `desktop_app.py`'s `_build_live_resolver()` helpers **only construct** a credential-requiring source (`AcoustIdApiSource`, `SpotifySearchApiSource`/`SpotifyApiIsrcSource`) when its env var(s) (`ACOUSTID_API_KEY`, `SPOTIFY_CLIENT_ID`+`SPOTIFY_CLIENT_SECRET`) are actually set — an absent credential means the rung is `None` and the resolver's own optional-rung design skips it, so `resolve()` can never raise for a missing-credential reason in production. `continuous_capture.py`'s per-track try/except and `desktop_app.py`'s whole-loop try/except remain as backstops for genuinely unexpected errors (transient network failures on a rung whose credential *is* present).
- **MB name search has no production backend yet** — only the `Protocol` and an `InMemoryMusicBrainzNameSearchSource` test fake exist. Both `cli.py` and `desktop_app.py` wire `mb_name_search=None`. Known scope gap, not a regression — tracked as follow-up, distinct from AC8's deliberate deferral below.
- **Normalization (AC4)** strips `feat./ft./featuring`, parenthetical/bracketed noise (`(Official Video)`, `[Lyrics]`), and remaster-year suffixes; casefolds; normalizes dashes/quotes/whitespace. Deliberately **keeps** Live/Remix/Radio Edit suffixes — those are distinct recordings, not noise. This normalized name key is only used as the *last* waterfall rung and never touches `canonical_track_id()` or any existing stored batch-path key.
- **Provenance sidecar (AC5).** Every embedding written by the live path carries raw title, raw artist, `app_id`, `captured_at`, and the chromaprint fingerprint alongside the resolved identity — so a later re-resolution or audit can trace exactly what was captured, not just what it resolved to.
- **Negative cache, schema-versioned (AC6) — a scoped revision of decision `dddc4d90`.** `dddc4d90` established persist-only-terminal (only fully-resolved MBID hits get cached; misses are re-walked every run) for the batch waterfall. `LiveNegativeCache` (`<data_root>/identity/live_negative/v{schema_version}/<encoded_key>.json`) intentionally revises this **for the live path only**: MB/AcoustID *misses* are cached too, with a ~30-day TTL (`NEGATIVE_CACHE_TTL_DAYS`), because live capture runs continuously and re-querying AcoustID/MB on every replay of the same unresolved track is wasted API budget in a way the batch path's one-shot runs are not. `IDENTITY_CACHE_SCHEMA_VERSION` gates the on-disk layout so a future schema change doesn't silently misread stale negative-cache rows. Wired unconditionally in both `cli.py`'s and `desktop_app.py`'s `_build_live_resolver()` — local, cheap, no credential gate needed.
- **Capture window bumped to ~120s (AC1).** `--duration` defaults for `capture-spike` and `capture-loop` moved from 10s/12s to 120.0s in `cli.py`; `desktop_app.py`'s `_CAPTURE_DURATION_S` likewise set to 120.0.
- **`fpcalc` setup (AC7).** `scripts/setup_collector.ps1` fetches the chromaprint `fpcalc.exe` release binary (pinned version, extracted to `.scratch/tools/`) if not already on `PATH`, alongside the existing WASAPI-helper and ONNX-model setup steps. `ACOUSTID_API_KEY` (and `SPOTIFY_CLIENT_ID`/`SPOTIFY_CLIENT_SECRET` for the Spotify rungs) must be declared in `.env.example` and set via `.env`/host env — never hardcoded.
- **Offset-spike experiment (AC8) deliberately deferred** — manual, hardware-dependent follow-up, not blocking this PR. Deferral recorded in decision episode `3c46007b-...-8fd809726fdc725`.
- **All tests fixture/mock-only (AC9)** — no live AcoustID/Spotify/MB calls in CI; `InMemoryAcoustIdSource`-style fakes and `respx` mocks throughout `tests/test_live_identity.py`, `tests/test_live_pipeline.py`, `tests/test_chromaprint_fpcalc.py`, `tests/test_continuous_capture.py`.
