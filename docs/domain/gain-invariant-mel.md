## Gain-invariant mel front-end (#194, grill 2026-09-07)

**Why this section exists.** #194 was scoped out of #170 as a pre-existing bug: the mel front-end feeds `log10(1 + _MEL_LOG_SCALE * mel)` to Discogs-EffNet with **no amplitude handling at all**. That transform is non-homogeneous — the `1 +` offset means scaling the input changes the *shape* of the log-mel surface, not merely its offset — so the same recording captured at two playback volumes yields two different embeddings. Playback volume is a property of the listening session, not of the track. In a first-write-wins, provenance-free pool, whichever volume happened to reach a track first is baked in permanently and unattributably.

- **Gain-invariance is the property, training-match is not** (decision `f0f66484-5fff-4519-91df-ef79c576514a`) — the AC buys `embed(a·x) ≈ embed(x)` for scalar `a > 0` and **explicitly drops** the "match what the model was trained on" framing the issue was filed with. That framing is unsatisfiable and unverifiable: Essentia's reference `TensorflowInputMusiCNN` chain does no amplitude handling either, the ISMIR 2022 paper reports training on commercial masters with no amplitude augmentation, and Spotify's client re-levels to ≈ −14 LUFS *upstream of our capture* — the mastered level is gone before we ever see it. This is a **documented accepted cost**, not a solved problem.
- **RMS to a fixed 0.1 (−20 dBFS) target** (same decision) — `mono * (0.1 / rms(mono))`. **Peak was rejected**: it cancels exactly, but it is set by a single sample, so one WASAPI start/stop transient rescales an entire 120 s window — cross-capture stability is a distinct property from gain-invariance, and peak satisfies the second while failing the first. **LUFS/EBU R128 was rejected** on correctness before dependency cost: R128's absolute −70 LUFS gate makes gated loudness non-homogeneous near the gate boundary, so it does not even deliver exact scalar cancellation.
- **The normalizer lives inside `_mel_patches`, after downmix and after resample** (decision `271c9acf-7b23-4da6-8585-7d048bc73c72`) — not in `run_inference`, which would transform the PCM handed to injected fake backends and muddy every orchestration test. Degenerate handling: RMS `< 1e-6` returns the input unchanged; clipping needs no special case (float32, no headroom constraint); **no gain cap** — a cap reintroduces level dependence for quiet captures, which is the bug.
- **Gate-before-normalize is an invariant, not a call-order accident** (same decision) — the raw-PCM RMS silence gate (`RMS_SILENCE_THRESHOLD = 0.01`, on both the replay path and the organic path) runs **upstream of** normalization and stays there. Normalizing first would amplify silence over the threshold and silently disable the gate on both paths. See `INVARIANTS.md`.
- **`EMBEDDING_SPACE_VERSION`, delete-don't-migrate** (decision `9bd3c2cd-3114-4d5c-9f91-3cedd80d9df4`) — a version string in `inference.py` covering the **front-end parametrization, not just the ONNX filename**, since the front-end is what changed. An unversioned `audio_analysis` record is pre-fix and is **deleted, not migrated**: organic captures cannot be re-derived (`RingBufferSink` never persists audio, by design), and decode-branch re-derivation was explicitly scoped out of this slice. `near_dup`'s `aliases.jsonl` is append-only and never rewritten, so **purging unversioned records purges the alias file too** — otherwise it keeps pointing at deleted keys. Blast radius on the author's device is zero: no `audio_analysis/`, no `data/pool/`, no `data/participants/` exists yet.
  - The version must actually be *persistable and readable*: `store.py` writes `model_version` only on the pool branch, `AudioAnalysisRecord` has no slot for it, and both readers drop it — so the versioning AC as first drafted was a no-op that would have condemned every new local record. The fix covers the root-branch payload, the dataclass field, and both readers.
  - Each record additionally carries the **applied gain / pre-normalization RMS** as one scalar. It is non-re-identifying, it makes the transform auditable across all three capture paths, and the schema is already being touched. Full capture provenance stays banned from pool records (decision `446d7d0a`).
- **Tests sit at `_mel_patches`, in two families** (decision `a5304b5d-520a-4c01-b6b2-f7c14515eb3b`) — the ONNX models are unavailable in CI and tests must not fetch them. (1) A float-rescale test at gains `1.0 / 0.1 / 4.0` asserting `rtol=1e-4, atol=1e-5`, which must fail on current code. (2) An **int16-quantized** test: WASAPI loopback converts `int16 / 32768.0`, so playback volume is applied *before* quantization and normalizing a quiet capture up also amplifies a fixed quantization/dither floor. The float-rescale test is invariant by construction and can never see that residual; the quantized test is what the issue's "within a stated tolerance" wording actually asks for. Degenerate coverage: all-zero frame and a clipped ±1.0 square, both asserting `np.isfinite(...).all()`.
- **Accepted cost: cross-track loudness is flattened** (decision `45747ed6-85ac-4b86-bc7d-03932f015631`) — normalizing every track to a fixed RMS discards mastering-loudness differences, which are a real if weak distinguishing signal. Consequently **`near_dup`'s `0.05` / `0.15` cosine thresholds and its `1e-6` hub-guard epsilon were calibrated against the un-normalized space and are unvalidated after this change.** No re-calibration in this slice — there is no pool to calibrate against. CMVN / per-patch mean subtraction was considered as an alternative and rejected: it removes spectral tilt, which is genuine timbre content the model uses.
- **Deferred out of this slice** — a coarse capture-path enum on pool records (#197, routed to #170's provenance thread, since it is a re-identification call), and the two remaining Essentia front-end fidelity gaps (#198): librosa's `norm='slaney'` unit-area filters vs Essentia's `unit_tri`, and librosa's normalized Hann window vs Essentia's `"normalized", false`.
