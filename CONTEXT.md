## Product framing

**One-line job:** show the user the **causal root** of their listening history — with evidence — so they can act on it (amplify / dampen / explore), instead of trusting an opaque streaming algorithm.

**Pillar order is causal, not parallel:**

1. **Understand** (primary) — derive roots from history. The product *is* this.
2. **Discover** (derived) — recommendations are downstream of root model; without a root, no recommend.
3. **Act** (byproduct) — playlist push, MCP surface. Side-effect of (1)+(2), not the goal.

This reorders the brainstorm's "3 pillars" (which presented them as parallel).

## Glossary

- **Root** — underlying driver that explains *many* surface listens (e.g. *"prefers fragile vocal timbres in evening listening"*). What this product surfaces.
- **Symptom** — surface listening pattern (top-artist counts, recent burst, genre frequency). What streaming services use directly. Symptom ≠ root; a tool that recommends from symptoms reinforces bubbles.
- **Retrospective** — analytical pass over history that derives roots with evidence, presented to the user.
- **Bubble** — local cluster of recent listening that crowds out the rest of the user's actual taste. Anti-bubble = penalty against the current bubble, computed from the *root* model not from raw recency cosine.
- **Evidence chain** — for any insight or recommendation, the ordered list of inputs/derivations that produced it. Must be inspectable by the user.
- **Root category** — a class of evidence used to derive roots. V0 ships three: `audio` (BPM/energy/valence/danceability cluster — i.e. scalar audio features that exist for any track regardless of genre), `temporal` (time-of-day / day-of-week / season pattern), `scene` (cultural/scene affinity via tags). V1 adds five more: `timbre` (deep audio-derived instrumentation signature: MFCCs, spectral envelope, instrument recognition), `career_phase` (artist-arc preference), `lyrics` (NLP themes), `structural` (song-form preference), `context_chain` (sequence/skip patterns). Naming note: `audio` was previously called `acoustic` (after the AcousticBrainz dataset) — renamed because "acoustic" is also one of Spotify's per-track scalar features (`acousticness`), and the dual use was ambiguous. AcousticBrainz the dataset keeps its proper-noun name.
- **Category weight** — per-user 0..1 scalar per root category indicating how much this category drives this user's taste. Excluded categories = 0. Lets the product fit users with very different listening modes (lyric-driven vs. pure-instrumental, scene-loyal vs. audio-driven, etc.).
- **V0 root model** — proxy approximation using only {audio, temporal, scene}. MUST be labelled as proxy in all outputs.
- **V1 root model** — full 8-category derivation, target precision. Includes audio analysis as a **deliberate killer feature** — no one else does it because it's slow/expensive; this project accepts that cost.
- **`RootProfile`** — versioned JSON artifact that *is* V0/V1 output. Top-level keys: `schema_version`, `model_maturity` (proxy/full), `snapshot_id`, `user_id`, `generated_from`, `category_weights`, `method_params`, `roots[]`, `tendencies[]`, `epochs[]`, `quality_log[]`, `analytics`. Canonical worked example: `schemas/root_profile.v0.example.json`. Source of truth for every downstream consumer (future Discover, MCP, dashboard, playlist).
  - **Per-root shape**: `id`, `category`, `classification` (`root`|`tendency`), `structural_descriptor` (category-specific), `evidence` (cluster_size/share, evidence_count, sample_tracks, coverage), `validation_scores` (confidence, temporal_stability, coverage_pass, confidence_pass), `epoch_presence`, `actionability_hint`, `curator_prose` (nullable), `caveats[]`.
  - **Root IDs are snapshot-local** in V0 — `r-audio-1` in one snapshot is not the same as `r-audio-1` in the next. Snapshot-to-snapshot matching is V1+ work (will add `linked_to_previous_id`).
  - **`tendencies[]` is structurally identical to `roots[]`** plus a `failed_tests[]` field — separated by section for cheap downstream dispatch, not by flag.
  - **`quality_log[]`** records every rejected candidate with the failed test and details. Mandatory under transparent-rejection invariant.
  - **`analytics`** is an open carve-out for future views (novelty curve, cluster_share_over_time). V0 fields are `null`; V1+ fills them.
- **RootProfile snapshot** — single `RootProfile` generated at a point in time. Per-user store keeps a *series* of snapshots so taste evolution can be analysed across years.
- **Enricher** — module that fetches/derives track metadata (ISRC, MBID, audio features, tags, scene) from Spotify / MusicBrainz dump / AcousticBrainz dump / Last.fm and writes it to the **shared metadata store**. Never per-user-specific.
- **Shared metadata store** — additive, multi-user-ready database of immutable-ish facts about tracks/artists. Refresh TTL ~90 days per entry. More users → more cache hits → faster analysis for everyone. (Mirrors the OOP-project pattern.)
- **Per-user store** — listening history (raw events) + RootProfile snapshots, scoped to one user.
- **`root` / `tendency` / `artifact_suspect`** — three-level validation classification of every candidate pattern. `root` passes all V0 tests (coverage + confidence + temporal stability); `tendency` is a visible pattern that failed at least one test (e.g. only in one chronological half, or below confidence floor) — surfaced separately, labelled, not called a root; `artifact_suspect` fails calibration / coverage floor and is suppressed from the user-facing artifact but logged in `quality_log[]` for transparency.
- **`evidence_coverage`** — per-root scalar: fraction of tracks in the cluster that have full metadata at the queried categories. Low coverage downgrades classification.
- **`temporal_stability`** — boolean+score from chronological-split test. Computed only when `n_unique_tracks > N_THRESHOLD` AND `history_span > T_THRESHOLD`; otherwise marked `not_evaluated` and the candidate is forced into `tendency`. Defaults: N=1000, T=6 months — both `(calibrate)`.
- **`quality_log[]`** — section of RootProfile listing every `artifact_suspect` plus the test it failed. We do not silently discard — we transparently show what was rejected and why.
- **Structural descriptor** — machine-readable summary of a root's evidence (for `audio`: `{bpm_band, energy_band, valence_band, danceability_band}` each in `{low,mid,high}` plus `centroid_raw` — the raw mean per clustered dim, so the band thresholds stay re-derivable; for `temporal`: `{time_bucket, conditioned_root_id, lift}`; etc.). The source of truth for what a root *is*. Every root has one; downstream consumers read this, not prose.
- **Curator prose** — optional human-readable label for a root, generated by an LLM strictly from `{structural_descriptor, sample_tracks, scene_context}`. The curator never introduces facts absent from its input; it renders, it doesn't infer. RootProfile is valid without curator prose.
- **`method_params`** — section per category capturing the actual algorithm hyperparameters used (HDBSCAN `min_cluster_size`, `min_samples`, etc.). Part of the evidence chain — two snapshots with different `method_params` are not directly comparable.
- **`time_bucket`** — coarse temporal slot used to test conditional patterns. Default partition is `day_part × weekday_kind × season`: day_part ∈ {morning, day, evening, night}, weekday_kind ∈ {weekday, weekend}, season ∈ {winter, spring, summer, autumn} → 32 buckets. The actual partition lives in `method_params.temporal_calendar` and is configurable; default 5/2 weekday split is a guess that will be overridable per-user when the V1 feedback channel exists (shift workers, non-standard schedules).
- **Conditional pattern (temporal root)** — a statistically significant `(time_bucket, conditioned_root)` association: `lift = P(conditioned_root | time_bucket) / P(conditioned_root)` above floor, plus event-count and stability tests. The temporal category does *not* cluster in its own feature space — it qualifies roots from other categories. `conditioned_root` is the id of a root from `audio`, `scene`, or (V1+) other content categories.
- **`epoch`** — a contiguous time-segment of the user's history where listening distribution is significantly different from neighbouring segments. Detected via sliding-window KS-test on cluster distributions. Epochs are *not* roots — they are historical context. They live in `RootProfile.epochs[]`, not in `roots[]`. Each root can carry an `epoch_presence` map indicating in which epochs it was active.
- **Change-point** — boundary between two epochs, with significance score from the KS test. Stored as part of the `epochs[]` timeline.
- **`scene` root** — a coherent tag-cluster derived from Last.fm track tags via NMF on the user's track×tag matrix. Each scene root carries top-K tags with weights, top-K artists in the topic, coherence score, and the chosen K (recorded in `method_params`). K is auto-selected over a small grid {3,5,8,13} by mean topic coherence above a floor; if no K passes the floor → `scene_roots = []` (honest empty).
- **Tag canonicalization** (V1 step) — optional synonym-collapse using lightweight embeddings before NMF. Each near-synonym group becomes one canonical tag; the full mapping is recorded in `method_params.tag_canonicalization` for transparency. Not in V0 pipeline.
- **Topic coherence** — mean pairwise **NPMI** (Normalized Pointwise Mutual Information, range `[-1,1]`) of a topic's top-`coherence_top_n` tags, measured over the user's own track×tag co-occurrence. `+1` = the tags always co-occur, `0` = independent, `-1` = never co-occur; the value is clamped to `[-1,1]` and a tag pair that never co-occurs scores `-1` directly (no smoothing). A topic with fewer than two tags scores `0.0`. Used to (a) select K (highest mean coherence ≥ floor wins, tie → smaller K), (b) gate topic acceptance (`coherence_score >= coherence_floor`, default 0.15). Low-coherence topics are degenerate — rejected to `quality_log[]` *before* validation, never handed to the #62 Validator.
- **Local data layout** — plain files, no DB. `data/history.jsonl` (append-only events), `data/cache/<track_id>.json` (mutable metadata pulled from shared store), `data/profiles/<iso>.json` (RootProfile snapshots), `data/state.json` (global pointers — schema version, last enricher run, etc.). Threshold to revisit: >500 MB total or >10 s load — then move to Parquet+DuckDB.
- **Pull-and-cache** — analyser does one bulk query to shared metadata store for all tracks of interest, materialises the result to local `data/cache/`, then runs the full analysis offline. New facts derived during the run that belong in shared store get a write-back step at the end. Per-track Supabase round-trips during analysis are forbidden.
- **`ListenEvent`** (event schema) — the source-agnostic unit of the per-user history store (`data/history.jsonl`, one JSON object per line). Shape: `track` (a `TrackRef`: optional `spotify_id`/`isrc`/`mbid` filled by the identity waterfall + always-present `name`/`artist` fallback) + `played_at` (timestamp) + `source` (tag, e.g. `ifttt`/`spotify_extended`/`lastfm`) + nullable `context` (a `PlayContext`: `ms_played`, `skipped`, `incognito`, `conn_country` — all independently nullable). Designed so a rich Spotify-extended / IFTTT extended-history row (carries play-context) and a thin Last.fm scrobble (no play-context) both land without a schema rewrite. `incognito` (private-session flag) and `conn_country` (ISO-3166 country of the play, the timezone-resolution input) were added for the `spotify_extended` source (decisions `83bd6f76`, `d2c1ff60`); a source that lacks them leaves them `None`. Decision `709f0b23-f5e6-43ab-a90d-ca0748ae310e` (see §Architectural decisions). Pydantic models in `src/music_intel_mcp/models.py`.
- **Lossless import** — an importer is a *faithful projection* of its source, not an editorialised subset. Every row the source recorded that carries identity + a placeable timestamp becomes a `ListenEvent`, and the raw play-context (`ms_played`, `skipped`, `incognito`, `conn_country`) is carried verbatim. **Validity is an analysis-time, per-pillar policy — never an import-time filter.** Filtering at import is lossy and irreversible (you cannot recover the dropped rows to re-calibrate a threshold); filtering at analysis time keeps every threshold sweep-able against the same stored history. Decision `83bd6f76`.
- **Play-validity** — the analysis-time predicate for "this play is a taste signal, not noise". Provisional V0/V1 default: `ms_played >= 30_000 AND skipped != true`. The **30-second boundary is Spotify's royalty/stream-count threshold, not a taste boundary** — it is the point a play is monetised as a stream (raised to 2 min for functional-noise genres in 2024), inherited here only as a conservative provisional anchor, *not* an endorsed cognitive cut. The real cut is a **V1 calibration deliverable**: a threshold-sensitivity sweep over `{5, 10, 20, 30, 45}s` measuring how temporal-root output moves with the floor, feeding #87. Decision `e2d9ae98`. **Wiring resolved for #90 (decision `c69c6f17`):** the filter applies **only in the temporal-seed path** — never at import (lossless invariant) and never on the audio/scene seed (those key on track identity, not play validity) — via a **null-safe** predicate: a play is invalid iff it can be positively identified as noise, `(ms_played is not None and ms_played < 30_000) or skipped is True`. So a null `ms_played` / `skipped` / `context` (every IFTTT and thin Last.fm scrobble carries them null) counts as **valid** — kept, never dropped and never a `TypeError`; the filter only *removes* plays it can confirm are short-or-skipped. The 30 s stays a **hardcoded constant, not a `TemporalParams` field** (the LOCKED V0 param set stays untouched and the value is known-provisional). The threshold-sensitivity sweep is a **separate measurement issue** feeding #87, not part of this slice.

## Shared-store schema (V0)

The shared metadata store (Supabase Postgres) holds **anonymous track-level facts only** — no `user_id`, no `played_at`, no play-context in any table. Migration: `supabase/migrations/20260609000000_shared_metadata.sql`. Python client: `src/music_intel_mcp/shared_store.py`. Issue #60, decision `f7a9fcbd`.

Tables:

- **`tracks`** — canonical identity + denormalised display facts. PK is a **canonical string id** (`mbid:…` > `isrc:…` > `spotify:…` > `name:<casefold>\x1f<casefold>`), built by `canonical_track_id()` — the same waterfall #61 formalises. Columns: `id`, `spotify_id`, `isrc`, `mbid`, `name`, `artist`, `artist_id`→artists, `fetched_at` (TTL anchor). Indexed on spotify_id/isrc/mbid for the identity waterfall.
- **`artists`** — artist-level facts (`mbid`, `name`). Defined for #61 + future artist enrichment; V0's `TrackMetadataRecord` denormalises `artist` onto `tracks` and does not yet populate this table.
- **`audio_features`** — one row per track (PK = `track_id`): `bpm`, `energy`, `valence`, `danceability`, `acousticness`, `instrumentalness`, `source`. All nullable (partial enrichment is valid).
- **`tags`** — many rows per track: `(track_id, tag, weight, source)`, unique on `(track_id, tag, source)`. Scene/cultural tags from Last.fm etc.

`TrackMetadataRecord` (pydantic, `extra="forbid"`) is the **pull unit** — a track's `tracks` row + its `audio_features` + its `tags`, plus `fetched_at`. `extra="forbid"` is the structural guard that personal data can never leak into a shared-store record.

**Store access** is `SharedStore` (Protocol) with only **bulk** ops — `get_tracks(ids)` / `upsert_tracks(records)`; no singular getter exists, so the no-round-trip rule is enforced by the type. Implementations: `LocalSharedStore` (**V0 default** — file-backed JSONL persistent cache, atomic temp-file + `os.replace` rewrite, resumable, last-line-wins), `InMemorySharedStore` (ephemeral; real store in tests + offline fallback), and `SupabaseSharedStore` (network-only, lazy-imports the `supabase` optional extra, never run in CI). **The Postgres tables above are the deferred V2+ target — see decision `813de040`:** at single-user V0 the shared store's only edge (cross-user cache sharing) is nil, so V0 persists to the local JSONL and keeps Supabase as a flag-flip (`--shared-store supabase`) for when multi-user lands. `pull_and_cache(ids, store, cache, now, ttl_days=90)` serves fresh entries from the local `MetadataCache` (`data/cache/`), collects uncached/stale ids, and fetches them in **one** bulk call; stale (past-TTL) store entries are surfaced for re-enrichment, missing ids for enrichment.

## Identity resolution (V0)

The **identity waterfall** turns whatever id a history event happens to carry into the one stable join key the enrichers need — the MusicBrainz **recording MBID** (the key into the AcousticBrainz/MusicBrainz dumps for #63/#64). Python: `src/music_intel_mcp/identity.py`. Issue #61.

Waterfall, deepest rung wins: **`mbid`** (already present, passthrough) → **`isrc`** → MBID via the MB dump → **`spotify_id`** → ISRC (Spotify) → MBID. The rung reached is the `ResolvedIdentity.level` ∈ {`mbid`, `isrc`, `spotify`, `name`}; only `mbid` counts as *resolved* (`ResolvedIdentity.resolved`).

- **`IsrcMbidIndex`** (Protocol) — `lookup(isrc) -> mbid|None` (the single disambiguated best) **plus `lookup_all(isrc) -> list[str]`** (every candidate MBID), the dump leg. `MusicBrainzIsrcIndex` reads a prebuilt `<isrc>\t<mbid>` TSV extract — **multi-valued**: repeated ISRC rows accumulate into a candidate list (dup MBIDs collapsed, first-seen order kept). Path is **env-pointed** (`MUSICBRAINZ_ISRC_INDEX`, falling back to `$MUSICBRAINZ_DUMP_DIR/isrc_to_mbid.tsv`) and **never committed** — a missing file yields an empty index (honest low coverage, never a crash). `InMemoryIsrcMbidIndex` is the test fixture (accepts `{isrc: mbid}` or `{isrc: [mbid, ...]}`).
- **`SpotifyIsrcSource`** (Protocol) — `lookup(spotify_id) -> isrc|None`, the Spotify leg. Optional: when absent, spotify-only tracks are honestly flagged at the `spotify` level, not dropped. The live implementation is **`SpotifyApiIsrcSource`** (`spotify_api.py`, #87 AC-A): client-credentials token (cached in-memory to just before expiry), batch `GET /v1/tracks` (≤50 ids), ISRC from `external_ids.isrc`, backoff on 429/503 (`Retry-After` honored). It owns a **persistent JSONL sidecar cache** storing hits *and* misses keyed by bare spotify id, so a re-run — or a resumed, interrupted `warm` — skips ids already asked about (`scene-warm-negative-cache-resume`). `warm(ids)` is the batching prefetch (extra method, not on the Protocol); `lookup` is the Protocol contract (cache read, single-id fetch fallback). `GET /tracks` carries ISRC and is *not* one of our constrained endpoints.
- **`IdentityCache`** (`data/identity/<input-key>.json`) — keyed by the *input* canonical id, so a re-run with the same history **skips the waterfall entirely** (no re-resolution). Regenerable + gitignored, percent-encoded filenames (shared `encode_cache_key` with the metadata cache).
- **`ResolutionReport`** — keyed by input canonical id (deduplicated). Derives `counts` (per-level ledger), `mbid_coverage` (fraction resolved to MBID — feeds `generated_from.coverage_per_category`), and `unresolved` (input keys that did not reach MBID — **flagged, never dropped**, per the transparent-rejection invariant). `to_metadata_records(report, now)` writes resolved identities back to the shared store, keyed by the *resolved* canonical id (so the store dedups across users by MBID).

The same `canonical_track_id()` waterfall (mbid > isrc > spotify > name/artist) is the single source of truth for track keys — the analyser's unique-track counting now calls it directly (the old `analyzer._track_key` tuple was folded into it).

**Measured reality on the owner's real library** (120-track deterministic KZ-heavy probe against live MB/AB, decision `2b262dc9`). The history export carries `spotify_id`s, **not** ISRCs — so a bare ISRC→MBID index resolves **~0** on its own. Resolution is a **2-link chain**: `spotify_id → ISRC` (Spotify `GET /tracks`, the `SpotifyIsrcSource` leg) → `ISRC → MBID` (the MB dump). Wiring only one leg yields 0% MBID → honest-empty regardless of thresholds. Measured ceilings on the full chain: **ISRC→MBID 56.7%** unique / **62.3%** play-weighted; the URL-relationships path adds only +0.8pt over ISRC on the tail (**rejected** — not worth a second live call per track). The unresolved tail is low-popularity regional (KZ) music MusicBrainz does not index (resolved-set popularity 36.3 vs unresolved 17.7; 31/51 unresolved below popularity 20).
- **`resolve --with-spotify` fires the spotify→ISRC leg** (#87 AC-A, wired). Off by default `_cmd_resolve` still passes `spotify_source=None` (offline, spotify-only tracks flagged at the `spotify` rung). With `--with-spotify`, `plan_spotify_source(with_spotify, env, data_dir=…)` gates on `SPOTIFY_CLIENT_ID`+`SPOTIFY_CLIENT_SECRET` **presence** (missing → `error:` + rc 2, before any network — mirrors the `LASTFM_API_KEY` gate on `--with-scene`), builds `SpotifyApiIsrcSource`, `warm`s every history spotify id once (batched prefetch), then hands it to the resolver so the per-track waterfall reads the local cache. **Capability-drift caveat:** `IdentityCache` short-circuits on the *input* key before consulting `spotify_source`, so a cache written by a no-spotify run is stale for a later `--with-spotify` run — an honest-measurement run (AC-E) must start from a clean `identity/` dir. The expensive API path is independently deduped by the spotify JSONL sidecar, so this only re-walks the cheap in-memory waterfall.
- **Spotify's ISRC is not authoritative** (F9, documented limitation). Labels reissue/mislabel ISRCs; a wrong-but-present ISRC resolves to a plausible-but-wrong MBID with no signal that it happened. Accepted as a known V0/V1 error source — not corrected here, flagged so downstream calibration reads coverage as *approximate*.
- **One ISRC can map to many recordings — built, #87 AC-B.** The MB index is multi-valued; `disambiguate_mbids(mbids, *, ab_covered=None)` picks one: **prefer an AcousticBrainz-covered recording** (the join we actually need has features), then **tie-break by the smallest MBID** so the choice is deterministic across runs. The `ab_covered` predicate is the AB dump's own presence check (`lambda m: ab_source.lookup(m) is not None`), threaded from `analyze`'s `audio_source` into the resolver so the *same* dump instance loads once; `_cmd_resolve` (no AB source) falls back to smallest-MBID, which does not change MBID coverage. The dump→TSV builder is `mb_dump.build_isrc_mbid_tsv(isrc_dump, recording_dump, out)` (offline, joins raw MB `isrc`→`recording`→`gid`; memory bounded to referenced recording ids), exposed as `music-intel build-mb-index`. Raw dump stays outside the repo.

## Artist identity resolution (#102)

The **artist waterfall** — sibling of the track waterfall above, keyed on the artist instead of the recording. Turns a Spotify artist URI (or, failing that, a bare artist name) into a MusicBrainz **artist MBID**. Python: `src/music_intel_mcp/artist_identity.py`. No AcousticBrainz join on this leg — artist MBID is a resolution target in its own right (report-only coverage), not a dependency of the audio/scene pipelines.

- **Waterfall, two rungs.** `spotify:artist:<id>` URI → MBID via a prebuilt `MusicBrainzArtistUrlIndex` TSV (`<uri>\t<mbid>`, built by `mb_dump.build_artist_mbid_tsv` from raw MB dump tables: `url` → `l_artist_url` relationship → `artist` row, three-pass memory-bounded join) → else **name-only**, unresolved. `ArtistIdentityResolver.resolve(uri, name)` returns a `ResolvedArtist` with `level ∈ {mbid, name}`; only `mbid` counts as *resolved*. A URI present but absent from the dump is **flagged, not dropped** — same transparent-rejection discipline as the track waterfall.
- **Name-match rung exists as a seam, unshipped by default (mirrors decision `2b262dc9`'s track-side call).** `ArtistIdentityResolver(index, name_index=...)` accepts an optional casefolded-name→MBID index; when wired it resolves name-only refs (chiefly Marquee entries, which carry no artist URI at all). No such index ships in V0/V1 — fuzzy/transliterated-name matching against MusicBrainz is the same precision minefield the track-side name rung was deferred over. A URI-backed lookup always wins over the name index when both are available.
- **`canonical_artist_key(uri, name)`** — `uri:<uri>` when a URI is present, else `name:<casefolded name>`. This is the **dedup key** for `resolve_all`: an `ArtistRef` and a `MarqueeEntry` for the same real-world artist do **not** collapse if one carries a URI and the other doesn't (URI-keyed vs name-keyed are different canonical keys) — dedup is strictly by key equality, never by display name.
- **`ArtistIdentityCache`** (`data/artist_identity/v<schema_version>/<input-key>.json`) — same terminal-only caching discipline as `IdentityCache` (decision `dddc4d90`): only `mbid`-level resolutions are persisted, so an unresolved name-level miss is re-walked on the next run rather than trusted as a frozen negative — a since-grown MB index is never masked by a stale miss.
- **`ArtistIdentityResolver.resolve_all(artists, marquee)` → coverage report.** Same shape as the track `ResolutionReport`: `n_unique` (post-dedup), `counts` (per-level ledger), `mbid_coverage`, `unresolved` (flagged input keys). The `import-account` CLI (#97) runs this over liked + followed + banned + playlist artists and **prints, then discards** the coverage — report-only, never persisted to `library.json`, identical discipline to the track-identity measurement already in that CLI.
- **Measured baseline (#114, 2026-08-19 MB dump build).** `import-account --artist-index` against the owner's real Spotify Account Data export (7996 likes, 538 followed, 6 banned, 3775 Marquee) with `spotify_artist_to_mbid.tsv` (439,500 pairs, built from the 2026-08-15 MB dump) wired in. The CLI's own reported number is a **blended 0.11 (457/4305)** across followed+banned+Marquee combined — but blending is misleading here, because the pool splits into two populations with structurally different resolvability, not just different join luck. Split independently (same index, same cache): **followed+banned artists resolve at 0.84 (457/544)** — a strong number, in line with the track leg's 0.61 and the dump's real quality; **Marquee resolves at a hard 0.00 (0/3761)**, and always will, regardless of dump completeness.
  - **Why Marquee is 0.00, confirmed in code, not inferred.** Two stacking, deterministic reasons: (1) the raw `Marquee.json` export file itself is `{artistName, segment}` — Spotify does not include an artist URI in this file (unlike `YourLibrary.json`/`Follow.json`, which do); `load_marquee_file` (`account_data.py`) parses it verbatim into `MarqueeEntry(artist_name, segment)`, and `MarqueeEntry` (`models.py`, `extra="forbid"`) has no field to hold one even if the source ever provided it. (2) The resolver's escape hatch for URI-less entries — `ArtistIdentityResolver(index, name_index=...)`'s optional casefolded-name→MBID rung — exists in code but `_build_artist_resolver` (`cli.py`) never wires it (`ArtistIdentityResolver(index, cache=cache)`, no `name_index`), so every Marquee entry hits `resolve(uri=None, ...)` and falls straight to `level="name"` (never counted as resolved). This is not a dump-completeness or MB-join-sparsity problem — it is mechanical exclusion by construction, verifiable with no ambiguity from the two call sites above.
  - **Reporting implication.** The single blended number the CLI prints is not a useful health signal for the URI waterfall on its own — it's dominated by a population (Marquee, 87% of the denominator) that cannot resolve regardless of index quality. `followed+banned` coverage (0.84) is the number that actually reflects join quality; Marquee coverage is a distinct, separately-tracked gap that only closes by wiring the name-index rung (deferred, unshipped by design — same precision-minefield call as the track-side name rung, §above) — not by improving the dump.

## Validation / classification (V0)

The **validation core** is the category-agnostic deep module every derivation pipeline feeds candidates into. Python: `src/music_intel_mcp/validation.py`. Issue #62, decision `bce66b6e`. It is the *only* place the three-class verdict lives — audio/scene/temporal (#63–#65) build `Candidate`s and hand them here; they do not classify themselves.

- **`Candidate`** — a category-neutral summary of one derived pattern: `candidate_id`, `category`, `cluster_size`, `cluster_share`, `evidence_count`, `coverage`, `confidence`, optional `temporal_stability_score`, plus the pass-through `structural_descriptor` / `sample_tracks` / `actionability_hint`. The validator reads only the scalars; the descriptor rides through onto the resulting root/tendency.
- **`DatasetContext`** — `n_unique_tracks` + `history_span_days`, the dataset-wide facts the temporal gate depends on. Passed once per run (constant across candidates), not per candidate.
- **`Validator(params=ValidationParams())`** — `classify(candidate, ctx) -> Classified` (one verdict) and `validate(candidates, ctx) -> ValidationOutcome` (batch → the three RootProfile sections `roots[]` / `tendencies[]` / `quality_log[]`, input order preserved).

The four V0 tests and their order:

1. **G — calibration** (`evidence_count >= evidence_count_floor`, default 50) and **E — coverage floor** (`coverage >= coverage_floors["tendency"]`, default 0.3) are the **hard floors**: failing either → `artifact_suspect`, suppressed from the user-facing sections and logged to `quality_log[]` (G checked first — no evidence is a more fundamental failure than thin coverage; details match the schema example: `{evidence_count, floor}` resp. `{coverage, floor_artifact}`).
2. Survivors are at least a `tendency`. **E (root floor)** `coverage >= coverage_floors["root"]` (0.5) sets `coverage_pass`; **A — confidence floor** `confidence >= confidence_floor` (0.6) sets `confidence_pass`; **D — temporal stability** is evaluated **only** when the gate is open (`n_unique_tracks > N_THRESHOLD` AND `history_span_days > T_THRESHOLD_DAYS`) *and* the candidate carries a score — then it must clear `temporal_stability_floor` (new param, default 0.5, `(calibrate)`). Otherwise it is `not_evaluated` and the candidate is forced to `tendency` (we never assert stability we could not measure).
3. A candidate that fails **no** promotion test is a `root`; otherwise a `tendency` carrying `failed_tests[]` — `"coverage_floor"`, `"confidence_floor"`, `"temporal_stability"` (evaluated-but-low), or `"temporal_stability_not_evaluated"` (gate closed / no score). Failed tests accumulate.

Every threshold is read from `method_params.validation` (`ValidationParams`) — none hardcoded; they are placeholders until calibrated on the owner's real data in #66. Honest-empty holds structurally: zero passing candidates → empty `roots[]` with a populated `quality_log[]`.

## Audio root pipeline (V0)

The **audio** category's deep module — `history → enrich → cluster → describe → validate`. Python: `src/music_intel_mcp/audio.py`. Issue #63, decision `01ba9bb7`. Wired into `analyze()` as the first derivation stage; it is **opt-in by dependency** — it runs only when both a `SharedStore` and an `AudioFeatureSource` are supplied, otherwise the audio sections stay honest-empty.

- **Enrichment.** `enrich_audio_features(track_ids, store, source, now)` populates `audio_features` on the shared-store records by **MBID**, then writes back (bulk read + bulk write, no round-trips). `AudioFeatureSource` (Protocol, `lookup(mbid)`) has two implementations: `AcousticBrainzDump` (production; env-pointed JSONL keyed by `mbid` — `ACOUSTICBRAINZ_FEATURES_INDEX` › `$ACOUSTICBRAINZ_DUMP_DIR/acousticbrainz_features.jsonl`; **lives outside the repo**, missing file → empty index → honest low coverage, never a crash) and `InMemoryAudioFeatureSource` (tests). The `AudioEnrichmentReport` bins every considered track into exactly one of `enriched` / `already_present` / `missing_features` / `no_mbid` (transparent rejection) and reports `coverage` = fraction now carrying features. Tracks already enriched or lacking an MBID are never looked up.
- **Two feature roles** (`AudioParams`). `cluster_features` (default `[bpm, energy, valence, danceability]`) define the distance metric, the bands, and the raw centroid — a track must carry **all** of them to enter clustering. `feature_set` (those four + `acousticness`, `instrumentalness`) is the wider enrichment target: `evidence_coverage` = fraction of a cluster's tracks carrying *every* one of the six, and low coverage downgrades classification. The two extra dims are coverage signal in V0, not yet cluster axes.
- **Clustering.** `derive_audio_roots(records, track_plays, params, validation_params, dataset_ctx)` z-scores the cluster dims (per-dim, `std==0`-guarded), fits **`sklearn.cluster.HDBSCAN`** (`min_cluster_size`/`min_samples` from `method_params.audio`; `copy=True` so the input is not mutated — the z-matrix is reused for centroids/sample distances) once over the whole user population, and maps each cluster **1:1** to a candidate. HDBSCAN noise (label −1) is dropped. A population below `min_cluster_size` short-circuits to honest-empty.
- **Determinism.** Feature rows are sorted by canonical id before clustering and sklearn's HDBSCAN has no random init → identical input yields identical roots. Cluster→`r-audio-N` ids are assigned by descending cluster size, tie-broken by smallest member id, so the prominent root is `r-audio-1`.
- **Per-cluster outputs.** `structural_descriptor` = the four `*_band` (cut by `params.band_cutoffs`, `v<lo`→low / `lo≤v<hi`→mid / `v≥hi`→high) + `centroid_raw`; `evidence` = `cluster_size`/`cluster_share` (size ÷ clustered population) / `evidence_count` (= size) / `coverage` / `sample_tracks` (the `sample_track_count` members closest to the z-space centroid, each `{track_id, name, artist, distance_to_centroid}`); `confidence` = mean HDBSCAN membership probability; `temporal_stability_score` = `1 − |first_half_frac − second_half_frac|` of the cluster's plays about the global history midpoint (`None`→`not_evaluated` when the cluster has no timestamps). `curator_prose` stays `None` in V0.
- **Coverage, two senses.** The **enricher** `coverage` is a diagnostic for the enrichment step; the **category** coverage (`AudioDerivation.coverage`, fed to `generated_from.coverage_per_category["audio"]`) is the fraction of the user's records that carry usable cluster features.

Candidates are handed to the #62 `Validator` — the audio pipeline never classifies itself.

**The resolver→analyze bridge (P9) — built, #87 AC-C.** `analyze(events, ..., resolver=...)` walks each event up the `spotify_id → ISRC → MBID` waterfall in `analyzer._group_and_seed` *before* grouping, re-keying `plays`/`refs` by the **resolved** canonical id. So a `spotify:`/`isrc:` event that reaches an MBID collapses onto its `mbid:` key and its plays merge with any other event resolving to the same recording; the enricher (which joins on the record's MBID) then sees it. Resolution is **inline** (not read-back from a pre-populated store) and memoised per raw canonical id, so duplicate plays don't re-walk the dump; it shares the `IdentityCache` with the `resolve` command so no double live-API cost. Without a resolver the raw ingest identity is used unchanged (the honest-empty V0 path). The CLI builds the resolver for `--with-audio` (`_build_resolver`, `--mb-index` flag); the `spotify_source` leg is left as a seam for AC-A, so on the **real** history (spotify_ids, no ISRCs) the bridge is correct but still resolves ~0% MBID until the spotify→ISRC leg is wired — the bridge bears fruit on real data only once AC-A lands.

**AcousticBrainz is a frozen dataset — the binding constraint is feature-coverage, not MBID-coverage.** AB shut down / froze in **June 2022**; the owner's library spans Oct 2022 → Jun 2026, so every post-mid-2022 release has **no AB row regardless of MBID**. **Live-measured on the full real library** (#87 AC-E, whole-library run — not a probe): `P(features | resolved MBID)` = **37.6%** (10,098 / 26,886), MBID coverage **53.9%** (26,886 / 49,879 analyzable unique), so **end-to-end audio coverage = 20.2%** (0.54 × 0.38) of the library can get ready-made audio features — the rest is feature-less even when fully resolved. The join result, not MBID-coverage, is the finish line (the turnstile ≠ the finish line). Two consequences: (1) roots built from ready-made features are drawn from the pre-2022, Western-skewed slice — the mainstream the product exists to escape, so a low root count here is honest, not a bug (decision `8186bc56`'s hard constraint stands: never weaken a threshold to manufacture roots); (2) the ~20% AB-covered set is the **labeled validation set** for the audio-decomposition North Star — decompose the signal, check against AB's known-good features on the overlap. Ready-made-first is not just a warm-up; it produces the ground truth decomposition needs.

**AB features source + `build-ab-index` — built, #87 AC-E** (decision `d8b488ba`, mechanism substitution). The literal 590 GB AB low-level bulk dump is impractical, so `music-intel build-ab-index` fetches the resolved MBIDs from AB's still-live query API and distils them into the same compact `acousticbrainz_features.jsonl` the `AcousticBrainzDump` reads. `src/music_intel_mcp/acousticbrainz.py`, three layers (pure mapping / `respx`-mocked API client / resumable builder). Because AB *derives* highlevel from lowlevel, a highlevel hit implies a lowlevel row exists → bpm/energy are present whenever features are (empirically: all 10,098 feature rows carry all four cluster axes, zero highlevel-only). The builder is **resumable** — a per-MBID raw sidecar (`acousticbrainz_raw.jsonl`, hits carry scalars, misses carry `scalars=null` as a negative cache) means an interrupted fetch resumes from cache with no re-queries. The two-layer split (raw AB-native scalars cached separately from the mapped `AudioFeatures`, incl. unused `aggressive`/`relaxed`) is why the field mapping is **reversible** — a re-map costs no network. AB→`AudioFeatures` field mapping:

  | `AudioFeatures` | AB source | AB path |
  |---|---|---|
  | `bpm` | lowlevel | `rhythm.bpm` |
  | `energy` | lowlevel | `lowlevel.average_loudness` |
  | `valence` | highlevel | `mood_happy.all.happy` |
  | `danceability` | highlevel | `danceability.all.danceable` |
  | `acousticness` | highlevel | `mood_acoustic.all.acoustic` |
  | `instrumentalness` | highlevel | `voice_instrumental.all.instrumental` |

  `source = "acousticbrainz_api"`. Per-user AB caches live in the scratch data-dir (`data/petr/acousticbrainz_{raw,features}.jsonl`), outside the repo — never committed (AB data is CC0 anonymous track-level, but the *fetch list* is derived from personal history).

**First real roots on the owner's real library — the anti-bubble thesis demonstrated (#87 AC-E/AC-F).** With the AB features leg wired, `analyze --with-audio` produces the **first non-empty `RootProfile` on real data**: **2 audio roots + 8 temporal tendencies + 13 epochs** over 137,952 events / 51,409 unique tracks, from 10,098 clustered tracks. `r-audio-1` (`cluster_size=3070`, conf 0.79, mid-bpm / high-energy / low-valence / high-danceability) and `r-audio-2` (`cluster_size=1801`, conf 0.96) both clear the coverage + confidence floors → genuine roots. Temporal, once ≥1 audio root survives, **both** qualifies those roots with `epoch_presence` **and** generates its own 8 `r-temporal-N` tendencies (evening/winter, night/summer, …). **AC-F is VALIDATION, and it passes:** all 8 temporal tendencies stay tendencies — they clear `lift_floor=1.3` (lift 1.33–1.80) but fail `confidence_floor=0.6` (conf 0.07–0.145), so the locked thresholds cleanly separate 2 real roots from 8 weaker tendencies **with zero weakening**. The accept-side thresholds (`min_cluster_size=50`, `confidence_floor=0.6`) that V0 never exercised even in fixtures are now validated on real candidates. This retires the "root-presence invariants are vacuously true" finding (§V0 exit state finding D) for the audio + temporal categories.

## Scene root pipeline (V0)

The **scene** category's deep module — `history → tag-enrich → matrix → NMF → coherence-gate → describe → validate`. Python: `src/music_intel_mcp/scene.py`. Issue #64, decision `91229a71`. Wired into `analyze()` as the second derivation stage (after audio, before temporal); **opt-in by dependency** — runs only when both a `SharedStore` and a `TagSource` are supplied, otherwise the scene sections stay honest-empty.

- **Enrichment.** `enrich_tags(track_ids, store, source, now)` populates `tags` on the shared-store records, then writes back (one bulk read + one bulk write, no round-trips). `TagSource` (Protocol, `lookup(artist, track, mbid)`) has two implementations: `LastfmTagSource` (production; `track.gettoptags`, lazy `httpx`, key from `LASTFM_API_KEY`, weight = Last.fm's 0–100 `count`; **network-only, never run in CI**) and `InMemoryTagSource` (tests). Tags are *universal* — every track carries name+artist, so there is **no `no_mbid` bucket** the way audio has. `TagEnrichmentReport` bins every considered track into exactly one of `enriched` / `already_present` / `missing_tags` (transparent rejection); already-tagged tracks are never looked up. `coverage` = fraction carrying tags afterwards.
- **Stop tags.** `method_params.scene.stop_tags_version` (default `"v1"`) selects a small frozen set of library-management / sentiment / structural noise (`seen live`, `favorite`, `good`, `various`, `spotify`, …) stripped before the matrix. Deliberately small — genre/mood/era tags (incl. `female vocalists`, `90s`) are real scene signal and **stay in**. Synonym-collapse (tag canonicalization) is a separate V1 concern; an unknown version degrades to the empty set (no silent v1 filtering).
- **Matrix + NMF.** `derive_scene_roots(records, track_plays, params, validation_params, dataset_ctx)` keeps only records with ≥1 non-stop tag (docs sorted by canonical id; vocab sorted) and builds a weighted `track×tag` matrix (tag weight where > 0, else 1.0) plus a binary co-occurrence matrix. It fits **`sklearn.decomposition.NMF`** (`init="nndsvd"` SVD-seed, `random_state=0`, `max_iter=1000`) for each K in `K_grid_explored` (default `[3,5,8,13]`) that fits the data (`1 ≤ k ≤ min(n_docs, n_tags)`).
- **K auto-selection by coherence.** Each topic's coherence is mean pairwise **NPMI** over its top-`coherence_top_n` tags (see glossary). Per-K mean coherence is recorded in `SceneDerivation.k_coherences`. The K with the **highest mean coherence ≥ `coherence_floor`** wins, ties → smaller K. **No K clears the floor ⇒ honest-empty** (`k_selected = None`, `roots = []`, `quality_log = []`); the chosen K is written back into `method_params.scene.K_selected` for provenance.
- **Coherence gate.** Within the selected K, topics below the floor are rejected **before validation** to `quality_log[]` as `{candidate_id: "q-scene-<topic_index>", category: "scene", failed_test: "coherence_floor", details: {coherence, floor, K, top_tags}}`. Surviving topics become candidates.
- **Three distinct scalars** (matching the example's 0.69 / 0.95 / 0.42). A doc belongs to the topic that dominates its NMF row (argmax). **confidence** = mean topic dominance `w[i,t]/w[i].sum()` over the topic's docs (soft membership strength). **coverage** = fraction of those docs that are *majority* this topic (dominance ≥ 0.5). **coherence_score** = the NPMI gate value, carried through onto the descriptor.
- **Per-topic outputs.** `structural_descriptor` = `{top_tags (each {tag, weight}, normalised), top_artists (each {name, count_in_topic}, capped at top_artists_count), coherence_score, topic_index_in_K}`; `evidence` = `cluster_size` / `cluster_share` (size ÷ tagged-doc count) / `evidence_count` (= size) / `coverage` / `sample_tracks` (the `sample_track_count` docs of highest dominance, each `{track_id, name, artist, topic_weight}`); `temporal_stability_score` via the shared `_stability` over the global history midpoint. Candidate ids `r-scene-N` are ranked by member count desc, tie → smallest member id, so `r-scene-1` is the most prominent topic. `curator_prose` stays `None` in V0.
- **Coverage, two senses.** As in audio: the **enricher** `coverage` diagnoses the enrichment step; the **category** coverage (`SceneDerivation.coverage`, fed to `coverage_per_category["scene"]`) is the fraction of the user's records carrying any non-stop tag.

Candidates are handed to the #62 `Validator` — the scene pipeline never classifies itself; coherence rejections are prepended to the validator's own `quality_log[]`. `_history_midpoint`/`_stability` are imported from `audio.py` (shared temporal-split helpers; #65 consolidation flagged).

## Temporal root pipeline (V0)

The **temporal** category's deep module — `members → bucketize → lift → describe → validate`, plus epoch detection. Python: `src/music_intel_mcp/temporal.py`. Issue #65, decision `00f7e1eb`. Wired into `analyze()` as the **third** derivation stage (after audio and scene); unlike them it is **opt-in by upstream content**, not by enricher — it runs only when at least one audio/scene candidate *survived validation* as a `root` or `tendency` (artifact_suspects are not real patterns to condition on). With no surviving members its ordering guard returns `skipped=True` and the temporal sections + `epochs[]` stay honest-empty.

- **No own feature space.** Temporal does not cluster — it *qualifies* upstream roots by when they fire. The analyzer passes a `members` map (`r-audio-N` / `r-scene-N` → the candidate's member track ids), filtered to the surviving ids. `derive_temporal_roots(members, plays, *, params, epoch_params, validation_params, dataset_ctx)`.
- **Bucketize.** `bucketize(played_at, calendar) -> {day_part, weekday_kind, season}` assigns one timestamp to its calendar slot. Hours are **half-open** with a night wrap (`[23,6)`), ISO weekday and month are **inclusive** with a winter month-wrap (`[12,2]`). Each dimension falls back to `"unknown"` independently when the calendar leaves a gap. The default `temporal_calendar` (in `method_params.temporal`) yields 32 buckets (4 day_parts × 2 weekday_kinds × 4 seasons); it is fully configurable (a custom calendar with different names/ranges is honoured verbatim).
- **Lift.** For each surviving root R and each bucket, `lift = P(R | bucket) / P(R)` where `P(R) = events_of_R / n_total_events` and `P(R | bucket) = events_of_R_in_bucket / n_events_in_bucket` (the bucket total counts *all* roots' events, so a bucket where R is over-represented relative to its baseline scores `lift > 1`). The `(bucket, R)` pair with the strongest signal per root becomes a temporal candidate.
- **Two gates, two fates.** `event_count_floor` (default 30) is a **silent precondition** — a `(bucket, R)` pair with fewer than that many of R's events in the bucket is dropped without a log entry (too thin to even consider). Pairs that clear the count floor but fall below `lift_floor` (default 1.3) are **logged, not dropped**: a `q-temporal-N` `QualityLogEntry` with `failed_test="lift_floor"` and `details` carrying the lift (transparent-rejection invariant). Survivors become `r-temporal-N` `Candidate`s.
- **Per-candidate outputs.** `structural_descriptor` = `{time_bucket, conditioned_root_id, lift, p_root_given_bucket, p_root_overall, n_events_in_bucket}` (lift/probabilities rounded for display); `evidence` = `cluster_size`/`cluster_share`/`evidence_count` (all the count of R's events in the bucket) / `coverage` (1.0 — every counted event is, by construction, in-bucket) / empty `sample_tracks`; `confidence` = `p_root_given_bucket`; `temporal_stability_score` = the chronological-split balance of the in-bucket events about the global history midpoint; `actionability_hint` = `"amplify root <id> with new candidates during <weekday_kind> <season> <day_part>s"`. Candidates rank by event count desc, tie → id then bucket key, so `r-temporal-1` is the most-evidenced pair.
- **Epochs.** `epochs[]` are detected independently of lift, by **sliding-window KS-test** (`scipy.stats.ks_2samp(left, right, method="asymp").pvalue`) over a per-event dominant-root-code array, stepping `step_days` with a `window_days` half-window each side; a window pair needs ≥5 events on each side to be tested. A boundary is a change point when `p < ks_significance_threshold` **and** it is at least one window past the previous change point (spacing guard against double-counting one transition). **Option B convention** (matches `schemas/root_profile.v0.example.json`): the change-point p-value is attached to the epoch the change point *ends* (the earlier of the adjacent pair); the final epoch's `change_point_in_significance` is `null`. Each epoch carries its `dominant_roots` (top-2 root ids by event count in the segment) and `n_events`. Epochs are **not roots** — they are historical context and live only in `RootProfile.epochs[]`.
- **`epoch_presence`.** After epochs are cut, each surviving root/tendency gets an `epoch_presence` map (`epoch_id → fraction of that epoch's events that belong to the root's members`), so a downstream consumer can see in which eras a root was active. The analyzer copies this onto the matching `roots[]`/`tendencies[]` entries.

Candidates are handed to the #62 `Validator` — the temporal pipeline never classifies itself; lift rejections are prepended to the validator's own `quality_log[]`. `_history_midpoint` is imported from `audio.py`.

### Temporal interpretation layer (#90 — validity filter + local-tz bucketize)

#90 corrects two things about the play stream this pipeline consumes, both resolved via `/grill`. The pipeline mechanics above are unchanged; only *which plays, in which zone* reach them differs.

- **Local-wall-clock plays (decision `498eb9d1`).** A new `analyzer._temporal_plays()` builder reads `event.played_at` / `event.context` / `event.source` **directly from the event list** — not the shared audio/scene `plays` map, which is naive→UTC coerced at `analyzer.py:99` (feeding that map in would double-coerce). It localizes each play *before* `bucketize`, source-keyed: `spotify_extended` always shifts (per-play `conn_country`→IANA region, else the user's modal mapped zone), IFTTT never shifts (already local). `bucketize` is untouched — it reads `.hour`/`.isoweekday()`/`.month` of whatever datetime it is handed. IANA regions only (never `Etc/GMT±N`), so DST/historical transitions like KZ 2024 are honored.
- **Two maps, not one (decision `77111ce0`).** `derive_temporal_roots` takes a **validity-FILTERED** localized map (feeds `bucket_totals` + per-root lift + `_balance` stability — the *taste* signal, via decision `c69c6f17`'s null-safe `ms_played≥30s ∧ ¬skipped` predicate) **and an UNFILTERED** localized map (feeds epoch detection only). Filtering epochs would let the non-stationary skip rate manufacture spurious change-points, and the threshold-sensitivity sweep **cannot** catch it (the sweep varies the *threshold*, not the *mask*) — so epochs run over the raw behavior stream while lift/stability condition on valid plays. Additive signature change to the locked #65 module, within #90's mandate.
- **Membership vs timing (intentional, not a bug).** Root *membership* is identity (all of a track's plays), but temporal *lift* conditions on valid plays only — a root can therefore show lift over a play subset smaller than its member count. This is the intended reading (membership = "is this track mine", lift = "when do I really listen"); an optional V1 filter-sensitivity flag is noted, not built.

This layer stays enrichment-gated + member-conditioned like the rest of temporal: it only runs when ≥1 upstream audio/scene root survives validation.

- **Validity-floor calibration is measurement-designed, not eyeballed (#95 → #98, decision `c6dcf6af`).** Three confounds make a naive floor sweep unreadable, and the #95 harness instruments all three: (1) the `skipped` predicate independently removes short plays at every floor (25% skip rate in the real export), so a per-floor cross-tab (`ms<floor` × `skipped`) + one skip-ignored run attributes movement between the two predicates; (2) `event_count_floor=30` drops candidates *silently* (no quality_log), so most verdict flips are count-cliff artifacts unless the drop is attributed harness-side; (3) `_history_midpoint` is recomputed from the *filtered* map, so stability deltas mix midpoint drift with signal — reported per floor. The read is against **pre-registered criteria** (16–19h peak survival + split-half test-retest agreement), never raw candidate counts. The decision to move `MIN_VALID_MS` lives in #98, `/grill`-gated.
  - **Run against the real export (137,952 events, reported to #98).** The validity cross-tab is a smooth monotonic falloff across all 9 floor configs, no elbow. Both pre-registered criteria came back inconclusive rather than favoring a floor: evening-peak survival is **False at every floor**, including 0ms — not a filtering artifact, the raw unfiltered hour histogram's true 3h-rolling-sum argmax starts at 17h, beating the 16–19h window by 0.3%, so the exact-window check is too strict to survive that near-tie and carries no discriminating signal. Split-half agreement ranges 0.641–0.688 with no floor standing out (n=64 compared candidates throughout — `n_surviving_upstream_roots=2` on this dataset). Report is local-only (`data/petr/sweep_validity_floor_report.json`, per the data-locality rule) — full detail is in the #98 comment, not committed here.
  - **#98 resolution: `MIN_VALID_MS` stays 30 000ms, decision `9301c09d`.** CRITIC loopback on the sweep read caught an overclaim: "no floor beats the incumbent" was being read as validating 30 000ms, but the evening-peak criterion fails identically at *every* floor including the unfiltered baseline, and split-half agreement is noise-dominated at n=64 — the sweep had no statistical power to distinguish floors at all, so a flat result is "instrument can't see an effect," not "no effect exists." The decision to keep 30 000ms is correct as a *default* (no cost to waiting, no floor in range looked better), but is recorded as **unvalidated-pending-better-instruments**, not confirmed. Fixed in the same pass: `_evening_peak_survives` (`scripts/sweep_validity_floor.py`) now checks a cyclic **±1h tolerance** around the 16h window instead of an exact match — the exact-match version was structurally incapable of ever discriminating floors (0/9 configs passed, including the null case). Deferred to a follow-up issue: whether `n_surviving_upstream_roots=2` / split-half agreement of 0.64–0.69 signals the whole temporal-root feature is underpowered on small-N libraries, independent of floor choice.

## History ingestion (V0)

The owner's listening history arrives as a directory of **IFTTT "Spotify → spreadsheet" `.xlsx` exports**. `src/music_intel_mcp/ingest.py` is the adapter; `music-intel import-ifttt --from <dir> [--data-dir ...]` merges it into the per-user `history.jsonl`. Issue #76. This is the only source-format-specific code — everything downstream sees source-agnostic `ListenEvent`s (`source="ifttt"`).

- **Workbook shape.** No header row. Columns, in order: `(played_at_string, track_name, artist_name, spotify_track_id, spotify_url)`. The id is **bare** (`56O4Wl...`, no `spotify:track:` prefix) → maps straight onto `TrackRef.spotify_id`, canonical id `spotify:<id>`. The url (col 4) is ignored.
- **Timestamp form.** `"December 3, 2024 at 12:31AM"` — parsed by `parse_ifttt_timestamp` (`%B %d, %Y at %I:%M%p`, padding-lenient). Minute resolution; no seconds.
- **Row tolerance.** Fully-blank/trailing rows, rows with no identity (no spotify id *and* no name), and rows whose timestamp does not parse are skipped, never fatal — counts surface in the `IngestStats` the CLI prints. The real export had **1 date-only cell (`"June 7, 2026"`, no time-of-day) out of 34,676 rows**: skipped, never coerced to a fabricated clock time. Export *drift* shows as a large `skipped_unparseable` count (loud) rather than aborting on the first odd row. A row with no spotify id keeps its name/artist fallback identity.
- **Idempotent.** `load_ifttt_dir` concatenates all workbooks, dedups by `(canonical_track_id, played_at)` keeping first, sorts ascending by `played_at`. `import-ifttt` merges existing-history-first (so events from other sources survive) then dedups → re-running over the same dir yields the same file. `UserStore.replace_history` rewrites the file from scratch (vs `append_events`).
- **⚠ TIMEZONE CAVEAT — resolved for #90 (decision `498eb9d1`).** IFTTT records the trigger time as a **zone-less local wall-clock** string. Because #90 keys the localization shift on **`event.source`** (not on `conn_country` presence — IFTTT has none), IFTTT rows are treated as **already local and never shifted**: the wall-clock already *is* the user's local time, so the correct action is to leave it alone (the exact opposite of `spotify_extended`, whose `ts` is honest UTC and is always shifted forward). This is why #90 keys on source, not on a `conn_country`-presence gate — a presence gate would wrongly leave honest-UTC Spotify rows with a null country unshifted. **Residual limitation (documented, not fixed):** IFTTT's wall-clock is the *account*'s configured zone, not the device's, so a traveling / zone-changing user smears across day-parts; `_temporal_plays()` logs the per-source unshifted count so the smear is at least visible. Moot on the owner's data — `import-spotify` source-supersedes IFTTT (decision `23fcf92c`), so zero IFTTT events survive there. See Open question 14.

## Spotify Extended Streaming History ingestion (V1 data foundation)

The **official Spotify data export** (`Spotify Extended Streaming History/`, a directory of `Streaming_History_Audio_*.json` + `Streaming_History_Video_*.json`) is the second history source. `src/music_intel_mcp/` gains a `spotify_extended` adapter; `music-intel import-spotify --from <dir> [--data-dir ...]` merges it into the per-user `history.jsonl`. Distinct from the IFTTT `.xlsx` path — it carries far richer per-play context and is the **V1 data foundation** (the real ~138k-play library the locked-not-calibrated thresholds of #87 will be calibrated against). Decisions `83bd6f76` (lossless import + schema), `e2d9ae98` (play-validity), `d2c1ff60` (timezone), `9576bde1` (row→event), `23fcf92c` (supersede), `822310b5` (slice scope).

- **Row shape (per Spotify's format spec).** Each JSON array element is one play. Load-bearing fields: `ts` (ISO-8601 UTC, **second-resolution**, = the time the track *stopped*), `ms_played`, `master_metadata_track_name` / `master_metadata_album_artist_name` / `master_metadata_album_album_name`, `spotify_track_uri` (`"spotify:track:<id>"`), `reason_start` / `reason_end`, `shuffle`, `skipped`, `offline`, `incognito_mode`, `conn_country` (ISO-3166), `ip_addr`. Podcast/video rows instead carry `spotify_episode_uri` + a null track name. The bare id inside `spotify:track:<id>` maps onto `TrackRef.spotify_id`, canonical id `spotify:<id>`.
- **Empirical ground truth (owner's real export, measured read-only).** 137,979 audio plays, 51,409 unique tracks, 17,992 artists, Oct 2022 → Jun 2026 (~3.75 yr). `ms_played` buckets: <5s 18,125 · 5–30s 12,369 · 30–60s 6,017 · ≥60s 101,468. `skipped=true` on 34,735 (25%). Provisional valid plays (`≥30s & !skipped`) = 99,729 (72%). `conn_country` 96% `KZ` → owner tz ~UTC+5 (Almaty); temporal peak 16–19h **local** (evening) vs 11–14h UTC — **timezone choice is load-bearing** for day-part buckets. 1 row without a track uri; 136 incognito; 1904 offline; podcast/video 7 of 137,985 (0.005%).
- **Lossless projection (audio tracks only).** Every audio-track row with an identity + a parseable `ts` becomes a `ListenEvent(source="spotify_extended")` carrying `PlayContext(ms_played, skipped, incognito=incognito_mode, conn_country)`. **No import-time validity filter** — `ms_played`/`skipped`/`incognito` are *carried, not applied* (see *Lossless import* + *Play-validity* in the glossary). Podcast/video rows (`spotify_episode_uri`, null track name) are the **one** kind dropped — they are not track plays and cannot enter a track-level pipeline; the drop is counted, not silent. A row with neither track uri nor track name is skipped (no identity), tallied like the IFTTT path.
- **Timezone — wiring resolved for #90 (decisions `d2c1ff60` + `498eb9d1`).** Temporal day-part/season buckets condition on **local wall-clock**, not raw UTC. `spotify_extended` rows carry honest UTC `ts` (unlike IFTTT's zone-less wall-clock), so #90 always localizes them: per-play `conn_country → IANA-region` map, else the user's **modal mapped zone** (their own most-common mapped country, computed from their data — *not* a hardcoded owner default), and raw UTC only if the user has zero mapped rows. **The zone-map values MUST be real IANA regions (e.g. `Asia/Almaty`), never `Etc/GMT±N` fixed offsets:** Kazakhstan unified UTC+6→UTC+5 on 2024-03-01 and the owner export straddles it (~1.4 yr affected), so a fixed offset would erase the transition and mis-bucket half the export by 1 h at the 23:00 evening↔night edge; `zoneinfo` honors the transition only when given a real region (adds a `tzdata` runtime dep on Windows — no bundled IANA db). A fixture test pins this (a KZ play at 2024-02 vs 2024-04, both 23:30 UTC, must land in different local hours). On real data 96% KZ shifts the listening peak from 11–14h UTC to 16–19h local — bucketing on UTC would mislabel evening listening as midday. Wired in a new `analyzer._temporal_plays()` builder that reads `played_at`/`context`/`source` **directly from events** (never the audio/scene `plays` map, already naive→UTC-coerced at `analyzer.py:99`), so `bucketize` itself is unchanged. **`_localize()` shifts by source-membership in `_UTC_STAMPED_SOURCES`, not a single-source equality check** — `spotify_account_history` (#103) is also honestly UTC-stamped (its own docstring: verified against 8,197 real plays, zero drift) and was initially missed, falling into the ifttt already-local branch and silently mis-bucketing every account-history play by its full UTC offset (caught by Code Review on PR #113, fixed same PR). It carries no `conn_country` of its own, so it falls back to the user's modal mapped zone the same way an unmapped `spotify_extended` play does.
- **Dedup + idempotency.** Key is `(canonical_track_id, ts.isoformat())` at **second** resolution (finer than IFTTT's minute grain), keep-first, sort ascending by `played_at`. On real data this collapses ~26 exact-second collisions (~0.02%) — accepted as negligible and noted, not specially handled (a genuine double-play inside one second is indistinguishable from a duplicate and vanishingly rare). `import-spotify` **source-scoped supersede**: it replaces the history contribution of `source ∈ {ifttt, spotify_extended}` (the two Spotify-derived paths describe the same underlying plays; the richer export supersedes the thin IFTTT rows) while **preserving events from any other source** (e.g. a future Last.fm scrobble import). Re-running over the same dir yields the same file. Decisions `9576bde1`, `23fcf92c`.
- **Dup-export inflation — already structurally closed, not a new dedup key (#93).** #93 was filed against the risk of double-counting plays re-shipped across two Spotify exports. Investigation found the source-scoped supersede above (decision `23fcf92c`) already closes this for the only source pair that currently re-ships full history (IFTTT superseded by `spotify_extended`; a from-scratch cross-source dedup key was rejected as redundant cost — Alt 2, rejected). What #93 actually added: (1) regression coverage for the real Spotify re-ship shape — export N+1 as a full-history **superset** of export N plus new plays, not a byte-identical re-import — proving supersede+dedup is lossless and duplicate-free across genuinely overlapping (not identical) exports; (2) a guardrail in `_cmd_import_spotify` (`cli.py`) that **warns, never blocks**, when a `spotify_extended` play in `before` predates the new import's earliest play — the signature of a re-export that is *not* actually a full-history superset of what supersede is about to drop, which would otherwise silently lose real history (Risk 1, accepted). First-ever import (empty `before`) is covered and does not trip the guardrail (Risk 3, accepted). **Unverified external-system assumption, not fact:** IFTTT is treated as "live per-event trigger, never re-ships history" (per owner's stated understanding) — this has not been independently verified against IFTTT's actual behavior and should be treated as a working assumption, not ground truth, until checked (Alt 3, accepted as documented-not-verified). **Deferred, not closed:** the current dedup key gives no protection against a *different* source (e.g. a future Last.fm scrobble import) reporting the same underlying play as an existing source — cross-source identity collision is out of scope here and tracked separately in #110 (Risk 2, deferred). Decision `9f9ed24f`.
- **Slice scope — honest measurement, not "first roots".** This importer's deliverable is the **canonical V1 data foundation + honest coverage measurement on real data**, NOT "the first temporal roots". Temporal derivation is *enrichment-gated* (runs only when audio/scene enrichment is wired) **and** *member-conditioned* (qualifies only audio/scene roots that survived validation); on the real export audio is 0% MBID and scene coherence 0.05 ≪ 0.15 floor → zero surviving members → temporal is honest-empty by construction, regardless of how time is handled. So `analyze` on this data is *honest-empty, not wrong*. The value delivered is: 51k live Spotify URIs to resolve, measured audio/scene coverage, and the stored `ms_played`/`conn_country` inputs the #87 calibration + enrichment-revival follow-up need. Decision `822310b5`.
- **Measured on real data — the honest-empty prediction confirmed (pipeline run, not probe).** `import-spotify → resolve → analyze` executed on the full export lands **137,952 events / 51,409 unique tracks / 1,361-day span**, single source `spotify_extended` (137,979 audio plays − 1 audiobook drop − 26 exact-second dedup collisions; unique count is an exact match to the read-only probe). `resolve` with no MusicBrainz dump installed puts **0/51,409 at MBID** (all resolve to spotify-level only) → `analyze` reports `audio=0.00 scene=0.00 temporal=1.00` and **0 roots / 0 tendencies / 0 epochs** — a *valid* honest-empty `RootProfile`, exactly as decision `822310b5` predicted. This is the #87 calibration baseline: the enrichment gate is unmet **because no dump is wired**, not because the data is thin. Installing a MusicBrainz ISRC→MBID index (`--mb-index` / `$MUSICBRAINZ_ISRC_INDEX`) is the first lever the enrichment-revival follow-up pulls. **→ Lever pulled (#87, since superseded):** the 6.1M-pair MB index + live Spotify→ISRC leg + AB features source are now all wired; the same `import-spotify → resolve → analyze --with-audio` chain now lands **2 audio roots + 8 temporal tendencies + 13 epochs** (MBID coverage 53.9%, `P(features|MBID)` 37.6%, end-to-end audio 20.2%) — see §Audio root pipeline "First real roots". Honest-empty was the *no-dump* baseline, not the ceiling.

## Explicit-preference ingestion — the "library" layer (#97)

The Spotify **Account Data** export (distinct from the Extended Streaming History) is what the user **told** Spotify, not what they passively played: liked tracks, followed/banned artists, saved albums (`YourLibrary.json`), playlists with per-item add timestamps (`Playlist1.json`, chunked `Playlist2/3…` for large libraries), and per-artist listener segments (`Marquee.json`). `src/music_intel_mcp/account_data.py` is the adapter; `music-intel import-account --from <dir> [--data-dir ...]` writes the single current-state document `data/library.json` (pydantic `Library`, `extra="forbid"`, `schema_version="v1"`). Grill decision `7e564052-f8e4-469e-a3d6-2182c26d11bb` locked the schema.

- **Explicit-signal layer vs implicit history.** History (`history.jsonl`) is passive listening events; the library (`library.json`) is the explicit-preference label layer — the ground-truth "yes / no / follow" the anti-bubble recommender scores *against*. Two separate stores, two separate importers; they never merge. Liked tracks and banned artists are distinct typed fields on `Library`, surfaced by `UserStore.load_library() -> Library | None` (None = honest-empty, no import yet).
- **Current-state document, not append-log.** `library.json` is the whole current library; re-import **replaces** it (the export is itself a full snapshot, so merging would double-count). Idempotent: re-importing an unchanged export writes a **byte-identical** file. The only non-deterministic field is `header.imported_at` (wall-clock); `preserve_import_timestamp(prior, new)` carries the prior stamp forward when nothing else changed, so an unchanged re-import is byte-stable (`_content_without_stamp` is the equality basis — everything except `imported_at`).
- **Identity is report-only, never persisted (decision `dddc4d90`).** Track signals reuse `TrackRef` (which gains an optional `album` field — backward-compatible with existing `history.jsonl` lines) and store `spotify_id` + name/artist/album only; `mbid`/`isrc` stay `None`. The CLI measures MBID resolution rate over liked + playlist tracks through the existing `resolve()` chain at import time and **prints it, then discards it** — the identity cache is the single home for resolved ids. `library.json` stores no resolved identity.
- **Artist-MBID resolution — report-only, same discipline as track identity (#102, superseding the earlier "out of scope").** Artist/album signals are stored losslessly as `ArtistRef`/`AlbumRef` (name + optional Spotify URI), un-resolved in `library.json`; the CLI additionally measures artist-level MBID coverage over liked + followed + banned + playlist artists through `ArtistIdentityResolver` and **prints it, then discards it** — same never-persisted discipline as track identity. See §Artist identity resolution (#102).
- **Marquee is verbatim, name-keyed.** `MarqueeEntry(artist_name, segment)` stores the segment string as-is (not normalized to an enum); the source carries **no artist URI**, so Marquee entries resolve on artist *name* only (the resolver's name rung, unshipped/unwired by default — see §Artist identity resolution) — a known limitation, not a bug.
- **Discover Weekly Archive is distinguishable by name, not schema.** Playlists carry `name`/`description`/`last_modified_date`/`number_of_followers` losslessly; the Discover Weekly Archive (Spotify's algorithmic picks the user kept) is identified by its playlist name at query time — no schema flag marks it.
- **Nothing dropped silently.** `AccountDataStats` counts every unmapped `YourLibrary` top-level key (`bannedTracks`/`shows`/`episodes`/`podcastChapters`/`other`, …) and every non-`spotify:track:` playlist URI (episodes, `spotify:local:` files); the CLI prints the full drop ledger. Only keys in `_MAPPED_LIBRARY_KEYS` (`tracks`/`albums`/`artists`/`bannedArtists`) are imported.
- **Diff vs prior.** `diff_libraries(old, new)` reports added/removed likes/bans/follows counts — likes keyed by `canonical_track_id`, artists by URI-else-casefolded-name — so an unchanged re-import reports all zeros. `old=None` (first import) reports everything as added.

## Spotify Account Data StreamingHistory ingestion — extending past the ESH tail (#103)

The Account Data export also ships a lightweight play log (`StreamingHistory_music_*.json`: `endTime`, `artistName`, `trackName`, `msPlayed`) alongside the explicit-preference signals `account_data.py` already imports. `src/music_intel_mcp/account_history.py` is the adapter; `music-intel import-account-history --from <dir> [--data-dir ...]` merges it into `history.jsonl`. Purpose: Account Data covers roughly the last 12 months and is available immediately, while a fresh Extended Streaming History (ESH) export takes weeks to arrive — this importer extends history *past* an existing ESH tail in the interim. Decision `5aaf6086-ec1f-426e-9884-984904ea44fc`.

- **`endTime` is direct UTC, not local wall-clock — verified against real data, not assumed.** Checked against 8,197 unambiguous plays matched by (track, artist) against the same user's `spotify_extended` `ts` across all 12 overlap months: every pair agreed within 60 seconds, no seasonal drift. This **overturns an earlier zone-reuse assumption** floated before the check — `endTime` is parsed directly as UTC, no zone-map or offset conversion.
- **Identity resolution is Spotify-only scoped, by design.** Account Data rows carry no `spotify_track_uri`, only `trackName`/`artistName`. To let a row share a canonical id with the richer ESH row for the same play (rather than permanently forking onto the `name:` rung), each row is looked up by `(name.casefold(), artist.casefold())` against a map built from the user's existing `spotify_extended` history; a key mapping to more than one `spotify_id` is dropped from the lookup (ambiguous) rather than guessed. This resolution is **deliberately scoped to Spotify-sourced history only** — generalizing identity resolution across arbitrary sources (YouTube Music, Apple Music, …) is explicitly out of scope for this importer.
- **Time-cutoff dedup, not identity-based merge.** Only rows with `played_at` strictly after the newest existing `spotify_extended` play are imported; if no ESH history exists yet, everything imports. Account Data carries no per-play context (no `skipped`/`incognito`/`conn_country`), so it must never shadow the richer ESH rows it overlaps with — merging by canonical identity instead of cutoff was rejected for exactly this reason.
- **Lossless projection + drop-accounting (mirrors #89 decisions `83bd6f76`/`9576bde1`).** No validity filtering at import time; every row this importer does not import (unparseable timestamp, no identity, before the cutoff) is counted on `AccountHistoryStats`, never silent.
- **Deferred: no reconciliation path on a future ESH re-import.** `spotify_account_history` is **not** in `spotify_extended.SUPERSEDES` — if the user later imports a new/extended ESH export whose range overlaps rows already imported by this module, the two coexist as separate events for the same play. Accepted as deferred during CRITIC disposition; a follow-up issue tracks the reconciliation design.

## Analyze CLI — enrichment surface (V0)

`music-intel analyze --user-id <id> [--data-dir ...]` loads the per-user `history.jsonl`, runs the derivation engine, writes a RootProfile snapshot, and prints a one-line summary plus per-category `coverage:` (audio/scene/temporal). Issue #78. The pipelines are locked (#63/#64); the CLI only *wires* the already-built source adapters into `analyze()` — no new domain logic.

- **Enrichment is off by default.** With no `--with-*` flag, `analyze` constructs no sources and emits the honest-empty V0 baseline (the audio/scene stages are opt-in by dependency, so they stay silent). This default is regression-guarded by the CLI tests.
- **Opt-in flags.** `--with-audio` runs the audio stage (needs an `AcousticBrainz` dump); `--with-scene` runs the scene stage (needs `LASTFM_API_KEY`). `--ab-index PATH` overrides the dump location (else `$ACOUSTICBRAINZ_FEATURES_INDEX` → `$ACOUSTICBRAINZ_DUMP_DIR/acousticbrainz_features.jsonl`). `--shared-store {local,supabase,memory}` (default **`local`**) chooses the metadata store: `local` is a persistent file-backed cache (path via `--shared-store-path`, default `<data root>/shared_cache.jsonl`) needing **no creds** and is the V0 default; `memory` is an ephemeral single-run store; `supabase` is the multi-user cloud cache, **deferred to V2+** (decision `813de040`) but still wired and fail-fast on missing creds.
- **Fail-fast on missing credentials, presence-only.** `plan_enrichment(args, env)` resolves flags → sources purely (offline, unit-tested). A flag whose credential is absent (`--with-scene` without `LASTFM_API_KEY`; `--shared-store supabase` without `SUPABASE_URL`+`SUPABASE_KEY`) aborts **before** touching history/store with a clear `error:` line and exit code 2. The env is checked for **presence only** — the secret value is never read or printed.
- **Credentials come from `.env` or the host env.** `main()` calls `load_dotenv(find_dotenv(usecwd=True), override=False)` once at startup, so a gitignored `.env` (copied from `.env.example`) populates `os.environ` for every subcommand. Anchored on the invocation dir (works from a source checkout and an installed wheel); the host env wins over `.env`; a missing `.env` is a silent no-op. `python-dotenv` being a declared dep but never invoked was a latent gap that silently broke this mechanism (#81).
- **Empty coverage is honest, not an error.** A dump that isn't installed or tracks that don't resolve to MBIDs yield `audio=0.00` (rc 0) plus a diagnostic `note:` — distinct from the credential-missing abort. A missing dump file is an empty index, never a crash (`AcousticBrainzDump` resolves its path lazily).

## V0 exit state (what "done" means)

The V0 epic (#58) exits on **pipeline correctness**, not on root presence. Decision `8186bc56` (supersedes the exit-lock decision `7b3adb41`); product-thesis follow-up tracked in #87.

- **Exit criterion = the engine runs end-to-end on the owner's real library and emits a *valid, honest-empty* `RootProfile`.** On petr's 21,118-track / 34,530-event / 553-day history the whole profile is honest-empty (0 roots / 0 tendencies). That is the system working as designed (the *Honest empty* invariant), not a failure — but the headline product (surfacing roots) was **never demonstrated on real data**. The thesis is **deferred to V1 (#87), not abandoned.**
- **Why empty — both root-producing pillars are structurally starved on V0-available sources.**
  - **Scene — coherence-starved (data, not threshold).** Last.fm yields 1.85% tag coverage; `derive_scene_roots` best mean NPMI is **0.0504 at K=3** vs `coherence_floor=0.15`, and it *worsens* with K (K=5 → −0.084, K=8 → −0.262, K=13 → −0.382). Finishing the Last.fm warm adds only the obscure scattered tail → coherence falls further. Not fixable by warming and explicitly **not** by lowering the floor (hard constraint).
  - **Audio — identity-starved AND a code gap (finding A).** 0% of tracks carry an MBID and `AcousticBrainzDump.lookup` is MBID-keyed → 0% audio ceiling regardless of dump quality. The zero is **over-determined**: even a populated dump would not help today because `analyze()` never wires the identity resolver into its seeding path (`_group_and_seed`, `analyzer.py:86-98`), `enrich_audio_features` keys on `record.mbid` (`audio.py:203`, always `None` for IFTTT tracks), and `analyze` never reads back the `resolve` subcommand's `IdentityCache`/store output. So "supply a dump" is necessary but **not sufficient** — the resolver wiring (#87 item 1) is the true prerequisite for any audio root. **→ Closed (#87, decision `4e2e49c7`):** the resolver→analyze bridge (AC-C) + live Spotify→ISRC leg (AC-A) + AB features source (AC-E) are all wired; measured MBID coverage is now **53.9%** (not 0%) and the audio pillar produces **2 real roots**. This finding is retired.
  - **Temporal — derivative.** Conditions on surviving audio/scene roots; with none upstream it is honest-empty by construction (category-ordering invariant).
- **Threshold provenance — locked for V0, validated-not-calibrated.** Every `method_params` default (`models.py`, the single source of truth) is **locked unchanged for V0** and validated *accept-side by synthetic fixtures* and *reject-side by the real run* — but **not empirically calibrated**, because V0 produced zero real candidates to calibrate against. Notably the audio HDBSCAN production values (`min_cluster_size=50`, `min_samples=10`) are **never exercised even in fixtures** (tests override to 5/2), and no accept-side threshold has ever seen real data. Empirical calibration is deferred to V1 (#87 item 4) and is **grill-gated** (calibration methodology trips the `/grill` stop-point); the hard constraint — never weaken a threshold to manufacture roots — carries forward.
- **Invariant coverage is uneven — exercised-green vs vacuous (finding D).** The honest-empty exit *exercises* the structural invariants (end-to-end run → schema-valid `RootProfile`, honest-empty, deterministic snapshot, `category_weights` inert) but leaves the *root-presence* invariants **vacuously true** (transparent-rejection of real candidates, coverage labelling, the confidence/stability/coverage promotion tests) — they pass only because no candidate ever reached them. Those are reclassified as carried, not satisfied (#87).
- **Known honest-empty limitations (carried, not bugs):**
  - **Audio transparent-rejection gap (finding G).** The audio honest-empty short-circuit (`audio.py:272`) returns an empty `quality_log`, so the 21,118 `no_mbid` drops — the dominant rejection reason on real data — leave **no trace** in the persisted artifact (only `coverage_per_category["audio"]=0.0`). Surfacing the `AudioEnrichmentReport` `no_mbid` bucket in the `RootProfile` is carried to #87.
  - **Temporal coverage is a static 1.0 (finding H).** `coverage_per_category["temporal"]` is hard-set to `1.0` in `analyzer.py` (not derived from data) — a placeholder that reads as "fully covered" while temporal is in fact honest-empty. Cosmetic at V0 (no temporal roots), flagged for #87.

## Invariants

- **Transparency.** Every insight, score, and recommendation carries its evidence chain. No opaque numbers. If we can't explain it, we don't ship it.
- **Causality.** The system models *roots*, not just symptoms. Symptom-only recommenders are explicitly out of scope — that's Spotify's job.
- **Actionability.** A root is only useful if the user can act on it (amplify, dampen, explore). "You listen to high-valence music" is trivia; "You listen to high-valence music exclusively on weekday mornings, never weekends" is actionable. Roots must be framed for action.
- **Discover ⊂ Understand.** The recommender cannot run before the root model exists. No standalone "Discover" path that bypasses root derivation.
- **Non-commercial honesty.** The product has no churn-cost for disappointing the user, so it deliberately surfaces high-variance / potentially-disliked candidates with reasons attached. Fear-of-disappointing is Spotify's constraint, not ours.
- **Batch-first, depth over latency.** No real-time requirement. A full analysis pass may take hours-to-days; the value lives in depth, not responsiveness. Compute budget is generous; new libraries/services are allowed when they buy precision.
- **Proxy outputs are labelled.** Anything derived from V0 root model (missing 5 of 8 categories) is shipped with an explicit "proxy / preliminary" marker. We never present V0 conclusions as final root.
- **Engine-first scope.** V0 and V1 both ship *only* the analysis engine + storage + enrichers + `RootProfile` artifact. No UI, no MCP server, no Discover/recommender, no playlist push, no dashboard. Those land in V2+, on top of a mature engine. Reason: anything built on a broken root model is wasted work.
- **Data persistence is permanent.** User history and RootProfile snapshots are kept indefinitely. A user returning a year later must find their prior data intact and analysable as a time-series. No "one-shot" runs that discard intermediate state.
- **Shared metadata, per-user analysis.** Track/artist enrichment is additive to a shared store visible to all users; analysis output (RootProfile) is per-user. Enricher writes only to shared; analyser reads shared + per-user history, writes per-user snapshot. ~90-day TTL per shared entry prevents API-cost-doubling. *V0 backs this store with a local JSONL file (`LocalSharedStore`), not the cloud — the shared store is anonymous-by-nature, so a cross-user cloud copy buys nothing until multi-user (V2+, decision `813de040`).*
- **History never leaves the user's machine.** Personal data (listening events, RootProfile snapshots) is local-only. Cloud holds only track-level metadata, which is anonymous by nature. Multi-device sync of personal data is a V2+ topic with an explicit user opt-in, not a default.
- **Honest empty.** An empty `roots[]` is a valid, correct output when the data does not warrant claims. The engine never fabricates roots to fill space. Returning "we have nothing confident to tell you" is the system working as designed; it preserves transparency more strongly than a hedged invented answer.
- **Transparent rejection.** Anything the engine considered but rejected goes into `quality_log[]` with the reason. We do not silently drop candidates — the user (or a future debugger) can always see what was thrown out.
- **Category pipeline ordering.** `temporal` is a qualifier on roots from other categories, so it must run *after* the categories whose roots it conditions. V0 order: `audio` → `scene` → `temporal` → `epochs`. Engine refuses to run temporal step if upstream categories have produced no roots and no tendencies (no content to condition on).
